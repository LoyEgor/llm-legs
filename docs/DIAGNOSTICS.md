# Diagnostics: llm-legs multi-account/limits ecosystem

For LLM sessions asked to fix limits, the menu, or claudeb. Read this before touching code.

## System map

- `llm-limits.sh` — read-only collector, writes `~/.llm-limits.json` (schema `{schema, fetched_at, vendors}`). A failed vendor refresh preserves its last valid buckets and records `vendors.<vendor>.refresh_error` as `{cause,at}` with optional `needs_user_entry:true`; passive collects preserve that outcome, and the next successful refresh of that vendor clears it. A full refresh with no successful vendor records the same base shape at top-level `refresh_error` and exits nonzero; partial and targeted failures exit zero. `--refresh` polls free usage endpoints; `--start-windows` is the only paid path (never call from scripts). `--table`/`--plain`/`--json` control rendering; piped output defaults to JSON.
- `bin/llm-refresh` — the escalating refresh driver behind the `com.llm-refresh` launchd heartbeat (`~/.local/libexec/llm-refresh-heartbeat` wrapper, 300s StartInterval; `bin/llm-refresh install-agent`/`uninstall-agent`). Per-vendor cadence state in `~/.llm-limits-refresh.state`, one JSONL line per vendor per due tick in `~/.llm-limits-refresh.jsonl` (`outcome` ∈ `fresh-passive|refreshed|partial|pushback|error`, plus OpenCode's own three below: `dormant|walled|reopened`; `partial` names the accounts still stale, and accounts no refresh can help — removed or auth-dead; worker-pool membership is spend consent and never gates a refresh — are never targeted and are listed as `unrefreshable:` in the detail instead of pinning the vendor at `partial`). Every vendor starts at 30 min on one ladder (15→22→30→45→60): a 429/rate-limit signal — from collector stderr or the store's `refresh_error` fields — loosens one rung, 72h with none tightens one rung, so per-vendor cadences diverge only from observed pushback, never by assumption. Step 0 is one passive collect shared across due vendors; step 1 runs `--refresh-account <vendor>/<account>` per still-stale account — except Claude, whose token endpoint is vendor-blocked: its step 1 splits the stale accounts by what `claudeb token-fresh <account>` says. A token that still carries a request needs no session — `claudeb revive` on it is one usage-endpoint GET — so EVERY such account is revived in the same tick, under the tick lock, `timeout`-guarded at `LLM_LIMITS_REFRESH_PROBE_TIMEOUT` (default 90s) and with no attempt stamp, since a live chat rotates its own token and must never wait for a session slot. Only an expired token needs `claudeb revive <account>` as a real session, and that is still one per tick (the least recently attempted of the expired accounts — every session attempt, success or failure, stamps `vendors.claude.attempts.<account>` in the state file, so a persistently failing account rotates out of the way instead of owning every tick; ties go to the stalest — `timeout`-guarded at `LLM_LIMITS_REFRESH_REVIVE_TIMEOUT`, default 240s; the rest wait for the next tick, and the detail says so, naming what it `probed:` and what it opened a `session:` for; Claude's reserved `main`/`-` names are `unrefreshable` too, since no revive can take them), followed by a collect so the rotated snapshot reaches the merged store. That interactive session holds no tick lock: the attempt stamp is persisted to the state file BEFORE the lock is handed back — otherwise a tick starting meanwhile picks the same account and opens a second session on it — the state is re-read from the file after the lock is reacquired, since whoever held it in between owns what is on disk, and a tick that cannot get the lock back stops there instead of racing the new holder through the remaining vendors. A revive that needs a human login — a login screen, or a usage 401/403 against a token it just rotated — makes that account `unrefreshable` and journals `error` — never `pushback`, which is reserved for a real 429 from the session. Tick lock `<state>.lock`, broken by holder liveness: a dead holder at once, a live one never until a 3600s ceiling, an ownerless directory after 1800s. OpenCode is the one inverted vendor: the Go plan publishes no usage endpoint, so there is nothing to collect passively and its only probe is a real completion. With no walled account in `~/.llm-limits.json` it is dormant — outcome `dormant`, zero requests, no passive collect started on its account — because every real call already records its own outcome (invariant `ai`). A standing wall is probed one `opencode-go wall-check` per walled account, which is free while the window is shut, and the tick lock is handed back while it is out so a wedged gateway holds no other vendor's tick. The probe answers in three states and the journal keeps them apart: outcome `walled` when the gateway repeats the 429, `reopened` when the plan SERVES the completion (the only thing that ends a wall, recorded as that account's served stamp — no record is ever dropped), and `dormant` when the wall went between the read and the request, so nothing was sent; the first two re-collect, so the rows every surface reads follow the probe. Whether a wall stands it asks the collector and never the record (invariant `al`). Its rung is read off the stated reset — day-granular, so approximate: within an hour of it, past it, or with none stated the ladder tightens and keeps probing, since only a served request ends a wall.
- `share/store-lock.sh` — mkdir-based lock serializing every read-merge-write of `~/.llm-limits.json`: `llm-limits.sh` re-reads previous state INSIDE the lock right before the jq merge, network stays outside, the write is an atomic `mv`, pid-owned with a rename-aside break by holder liveness — a dead holder at once, a live one never until a 3600s ceiling, an ownerless directory after 30s (env-overridable; only the owner may release), skipped entirely under `--no-write`. Concurrent collector invocations (heartbeat tick racing a menu refresh) can no longer drop each other's vendors.
- `bin/claudeb` — account prober/launcher. Snapshots per account in `~/.claude-profiles/.claudeb/limits/<name>.json`:
  ```json
  {"five_hour":{"used_percentage":6,"resets_at":1784044800,"as_of":1784031056,"origin":"usage"},
   "seven_day":{...}, "fable":{...}, "auth":{"status":"ok","checked_at":1784031056}}
  ```
  `origin` ∈ `usage|headers|cached`. `auth.status` is only ever `"ok"` or `"expired"` (never `needs re-login`/`auth_needed` — those are free-text `cause`s or Codex-only concepts, respectively).
  **Account existence is one set** (shared-invariants row x): `account_names` unions `tokens/`, `limits/*.json`, and the `~/.claude-profiles/<name>` dirs (reserved `main`/`-` filtered), and every verb — `status`, `enable`/`disable`, `warm`, probes, `use` pin validation — consults it, so a keychain-only browser login (no setup token) is as real as an `add`ed account. Account birth (`add`, first-launch profile create) fires a detached targeted collector refresh and removal fires a passive collect (`share/account-announce.sh`), so the menu follows without a manual refresh.
  **Display semantics are one view** (shared-invariants row y): `share/limits-view.sh` is the single definition of stale/expired/effective and of cell text (`limits_pct_text` = effective value + `~` stale / `!` expired markers, bare `-` when unmeasured; one reset formatter, one age formatter, age = oldest measured bucket). `bin/claudeb` and `llm-limits.sh` prepend `$LIMITS_VIEW_JQ`; the menu renders the collector's precomputed `effective_pct`/`stale`/`expired` fields. So "menu shows fresh, claudeb shows stale" is by construction impossible for pct cells — `tests/e2e_surfaces.sh` proves it live against the real store. Any probe/warm that rewrites snapshots announces one passive collect (`announce_limits_probed`; the collector suppresses its own children via `LLM_LIMITS_ANNOUNCE_SUPPRESS`), and a pressed `r` in the status TUI carries `CLAUDEB_WARM_USER_EXPLICIT=true` so the robot-refresh guard cannot silently eat it.
  Two independent OAuth-heal paths sharing `oauth-attempts.json`: **warm** (drives the real `claude` CLI's own OAuth rotation, zero-cost, comment at `bin/claudeb:632-635` — a token-endpoint 429/failed record must never gate it) and **direct refresh** (claudeb's own curl POST to the token endpoint, `oauth_refresh()`). `.claudeb-state` = current account name (single line); `disabled` = one excluded-account name per line, absent file = all enabled — this is the **worker pool**, and all four vendors now share it (`share/worker-pool.sh`, one file per vendor: `~/.claude-profiles/.claudeb/disabled`, `~/.codex-profiles/.codexb/disabled`, `~/.gemini-profiles/.geminib/disabled`, `~/.grok-profiles/.grokb/disabled`; the dot-directory keeps it outside the profile enumerators' `*` glob). Exclusion is a WALL for every headless run: `worker-pick` and `codexb pick` skip the account, and `claudeb … -p`, `codexb <name> exec`, `geminib profile … --print`, `grokb profile … --prompt-file` and `worker-run start --account <name>` refuse it outright — only the vendor pin in `~/.claude/worker-model` overrides. An interactive session is the user and is never gated, so any member may go out, the last one included; an empty pool then answers `every <vendor> account is out of the worker pool` and `worker-run` reports `OUTCOME: <VENDOR>_UNAVAILABLE`, never a usage limit. `claudeb enable|disable`, `codexb enable|disable`, `geminib enable|disable`, `grokb enable|disable`; the state is visible in each tool's own `list`/`status` (`(out of pool)`), in the table's `ROT` column (`off`), and as the menu checkbox.
  Entry points, and the whole reason there is no daemon: an **interactive** run must name a profile (`claudeb profile <name>`; bare `claudeb` and any argument list without `-p`/`--print` print the profile list and exit 2), while a **headless** run (`-p`/`--print`, i.e. a program calling claudeb — find-truth, usage-ai-report, any script) takes its account from `worker-pick --account claudeb` and then runs exactly the `claudeb profile <acct> …` path — in-process, so there is no second `claudeb` in the process tree. That path has no wall, no hold, and no retry: nothing selectable exits immediately with the query's own **3** (a caller choosing between "retry after the reset" and "this is misconfigured" needs those apart), a missing or unusable `worker-pick` exits 2, and no request is ever parked until it becomes a 503. `CLAUDEB_WORKER_PICK` overrides the binary (a sibling of the resolved script wins over `PATH`, so both halves of the query contract come from one checkout). Headless runs never restamp `.claudeb-state`. The `*` in `status`/`accounts` is a routing answer and not the last account launched: it is `worker-pick --account claudeb --role chat` (pool toggle respected, pin ignored — a pin overrides automatic work, never what a human launches by hand), and where that answers nothing no row carries it. `.claudeb-state` keeps its own meaning — the last profile launched, which `bin/chats`, `bin/chat-find` and `workflow-burn-gate.sh` read. `claudeb use <name>` writes the same `claudeb_profile=` pin in `~/.claude/worker-model` that `/worker claudeb <name>` sets — the pin every consumer already reads (worker-pick routing, `worker-limit-gate.sh`, the statusline `w:cb @`) — leaving `worker=` alone so naming an account cannot also re-route work to another vendor; `use` with no name prints the pin, `use --clear` removes it, an unroutable name is refused, and an out-of-pool account is accepted with a note that the direct pin overrides automatic pool exclusion.

- `bin/instruction-write-gate.sh` + `bin/instruction-watch.sh` + `share/instruction-files.sh` — the two doors on the files an LLM re-reads across sessions, deployed as symlinks from `~/.claude/hooks` and registered in `~/.claude/settings.json`: the gate on PreToolUse(Bash), the tripwire as `check` on PostToolUse and `baseline` on SessionStart. One table decides which rule a target answers to, `instruction_write_class` in the shared module, and every consumer asks it rather than carrying a list: **always** — the every-session class, the global `~/.claude/CLAUDE.md` (a symlink into `claude-setup`, and priced through the link at its own rate rather than the repository's), any project `CLAUDE.md`, any `CLAUDE.local.md` — denied whatever the byte delta and whatever Egor's autonomy span says, since these ride in the prefix of every session and no cleanup of them is a model's own call; **debt** — `.claude/review-debt-ignore`, denied always with its own reason and no cost figure, because a line written into it retires unreviewed work, which is the project's answer and never a model's; **span** — the on-demand instruction markdown under `~/.claude/docs`, `agents`, `instructions`, `skills`, `skills-on-demand`, `rules` and `commands` (`_instruction_class_dirs`, resolved through their symlinks into `claude-setup`, depth-unbounded), denied outside the span, and inside it denied only for a write that can GROW the file: `>`, `>|`, a `tee` with no append flag and a truncating interpreter mode pass; `>>`, `tee -a` and every appending mode do not. `~/.claude/settings.json` is out of the deny half entirely — nothing re-reads it into a context window, and the harness rewrites it on every model or permission-mode switch, so a denial there cost a tactical "ok" and caught nothing — while staying watched, since it is the one guarded file git cannot give back. The span has ONE definition, `rj_autonomous` in `../claude-setup/hooks/lib/review-journal.sh` reached only through `instruction_autonomous` (invariant row `br`), sourced in a subshell on the denial path and never on the hot one; an unreadable library or a missing transcript answers "no span", the stricter side. A shell command is judged by its write TARGETS: `instruction_shell_scan` drops heredoc bodies and collapses quoted runs carrying whitespace, so a scratchpad heredoc quoting a rule passes while a heredoc actually targeting a guarded file is denied, and a shell interpreter (`INSTRUCTION_INTERPRETER_RE`) or a command-position word the scan cannot resolve falls back to the raw command. What the gate can read before a call is the SHAPE of a write, so the bytes are the tripwire's: it compares every watched file against the session's baseline, reports each change with a restore command, and PUTS BACK growth only when all three of these hold — the file has a class, the call that just ran LEFT ITS BYTES in it, and the span stands. Where a command leaves its bytes has ONE parse for both doors, `instruction_write_targets` in the shared module (invariant row `br`): it walks the command into simple commands and yields a row per destination — a redirection operand (`>`, `>|`, `>>`, never a `<` operand and never an `&`-dup), every operand of a verb that writes each one it names (tee, an in-place editor, truncate/dd/patch/ed/ex), the last operand of a copy verb with a directory destination resolved to dir/basename, and, for an interpreter alone, any bounded occurrence of the name in the call, since there the path stands inside the payload rather than in an operand. A destination is matched WHOLE, so `CLAUDE.md.bak` is not the file. The gate reads only the redirect and tee rows and judges each one WHOLE — its own file's class against its own `trunc`/`append` mode — so a compound cannot grow one guarded file on a later row's ability to shrink another; the tripwire takes the rows that are a write by shape (redirect, copy verb, destination verb) and leaves out the loose interpreter rows, whose name came out of a payload the parse cannot read and whose revert would put back another chat's growth over a call that only read the file, on the RAW command so a heredoc target counts, since a heredoc body belongs to the command that declared it. The bytes it overwrites are parked beside the kept ones first, and the model is told in `additionalContext`. A shrink inside the span is never reverted, since that is the cleanup the span exists for, and outside the span nothing is rolled back at all: in a shared checkout the writer is as often another chat as this session. Every denial quotes that file's own re-read rate (`instruction_live_rates`, same numbers as the bloat gate), and the exact retry passes ONCE, so a deny costs Egor one round trip and never becomes a wall. Fail-open throughout: no `$HOME`, no `jq`, an unsourceable module or a malformed payload all exit 0. The Edit/Write path is priced rather than classed — `bin/instruction-bloat-gate.sh` denies growth past 120 bytes and lets a shrink through, so a shrinking Edit of an always-class file is reported by the tripwire and denied by nothing. - `bin/opencode-go` — OpenAI-compatible client for the OpenCode **Go** subscription only
  (`https://opencode.ai/zen/go/v1`, key from keychain service `opencode-go`, never in argv;
  `run` refuses any model outside the plan's `/models` list, cached 10 minutes). The Go plan's
  own usage percentage is not exposed by any endpoint — `usage`, `limits`, `me`, `account` and
  `responses` all answer 404, so an account has exactly two knowable states. Both are recorded
  here, at the request, for every caller, as raw observations and no verdict (invariant `ai`): a
  429 naming the plan appends one `jq`-built row to `walls.jsonl`, and a COMPLETION the plan served
  stamps `<state_dir>/worker-stats/opencode-seen/<account>`. Nothing is ever deleted and nothing
  expires: a 2xx from `raw models` is not a served completion, and the two stamps are read against
  each other by `llm-limits.sh` (invariant `al`). A store write that fails is never swallowed —
  the command exits non-zero even when the answer itself arrived, or a caller would read a wall as
  retired while the record still stands. `opencode-go wall-check` re-asks a standing wall with one
  16-token completion — free, since a 429 spends nothing — and sends NOTHING unless
  `~/.llm-limits.json` says the account is walled, because a successful call would spend the
  subscription to learn what the collector already answered; its first word is the state it
  observed, `walled`, `served` or `dormant` (nothing sent), and those are not interchangeable.
  That frugal walled-only path is what `bin/llm-refresh` drives, one bare `wall-check` per walled
  profile rather than a leg-wide sweep. `wall-check --all` is the same question asked for the whole
  leg in one command, and it belongs to the menubar: its `Hard refresh` passes `--all --probe-clear`
  (either order), which drops the walled-only gate and asks every account on the roster instead,
  spending one completion on each clear one: an account's age is the stamp of the last completion
  the plan served it, so current truth for a clear account cannot be had for less. Nothing
  scheduled passes it. Latency is decided by output volume, so
  reasoning is the whole game: `--no-reasoning` negotiates `reasoning_effort:"none"` →
  `chat_template_kwargs.enable_thinking:false` → a `</think>` assistant prefix → plain, because
  which one a model accepts varies **between requests for the same model** (a rejection is a hard
  400, and the prefix can make a model answer nothing at all, which retires that strategy too).
  The gateway's own ~190s **upstream idle timeout** is the root cause of every intermittent 503
  here (opencode#30002: a reasoning model emits no output token for 2-4 minutes, the connection is
  closed for inactivity, input tokens already billed; a configurable timeout and reasoning-token
  keepalive were both declined). It is not a local bug and there is no vendor status page, so
  reproduce a failure at least twice before chasing it in this repo. Some models — grok-4.5 and the
  deepseek family — ignore every reasoning-off knob and walk straight into that timeout, but they
  do honour an explicit `--effort low`: grok-4.5 reviewed a 54k-token diff in 8-91s over six runs
  with no failure, against 196-436s with 503s on the reasoning-off path. So a stall on such a model
  is a missing budget, not weather.
  Requests are buffered and retried on 5xx; a 5xx that arrives only after `OPENCODE_GO_SLOW_SWITCH_S`
  means the generation outlived that deadline, so the next attempt streams. A transport failure —
  curl exits non-zero and reports `000` because the gateway hung, reset or spoke bad HTTP/2 —
  counts as the same class, and is the case the escalation exists for — which helps only a
  model that actually emits tokens while working, never one that is silently thinking. A
  stream's stall detector (`OPENCODE_GO_STALL_S`) is its only deadline — it deliberately carries no
  `-m` cap, because any cap short enough to matter also kills a legitimate long generation
  (`deepseek-v4-pro` needs ~1000s). `minimax-m3` ignores every strategy and needs ~38k tokens of
  thinking before it answers, so it only works with a token ceiling above that, never below it.
  **An empty answer with exit code 0 is two different bugs, and the envelope names which.**
  `finish_reason:"length"` with empty content means the whole token budget went into reasoning and
  the answer never started — suppress reasoning (`--no-reasoning`) or raise the ceiling above the
  model's thinking, and never lower `--max-tokens` to "save" anything, because the budget is spent
  on thinking first. `finish_reason:"stop"` with empty content is the opposite: the model chose to
  end the turn, which is weak instruction following, not a budget — grok-4.5 does this when a
  review methodology is injected into its prompt (2 of 3 passes, after 88-122s), and the
  `</think>` prefill strategy can trigger it in any model. Neither case is a usage limit; a real
  wall is an HTTP 429 naming `limitName`. Because both symptoms look identical from the outside,
  read `finish_reason` before changing any knob.

- `bin/worker-pick` — token-free implementation-worker routing over the passive merged cache, implementing `docs/routing-contract.md` and nothing beyond it. It prints one flat cross-vendor ranking (`NEXT` rows, `ACCOUNT:` naming row 1) over a section per vendor; every Gemini profile reads only its normalized `Gemini Models` five-hour/weekly buckets. Selection is the contract's rules 1-3 (rule 4, reachability, is enforced by the vendor CLIs and `worker-run`, not here): a candidate is an in-pool account with live auth and a numeric **daily budget**, and the answer is the vendor pin when it can serve, otherwise the largest budget. One metric decides everything, `limits_daily_budget` over `limits_days_remaining` — both defined once in `share/limits-view.sh`, which is their only home and which no surface re-derives: what is left of the spending window divided by the days left in it, `(100 - pct) / days`, `pct` clamped into `[0, 100]` and `days` floored at 0.25 so a window about to roll cannot divide to infinity, while a reset the limits view refuses to print (a placeholder epoch, or one over a day past) answers null days and is read as a neutral 7-day window rather than the floor, so a garbage timestamp cannot rank an account first. Ordinary work is measured on the weekly bucket and the reset that bucket carries; a vendor reporting no weekly percentage at all is measured on its five-hour reading over the neutral window instead. The rank key vector is ascending and identical for all four vendors: `[five-hour deferral, fresh claim, late auth, −budget, name]`; an account is skipped for two reasons the output keeps apart: **walled**, which is the usage verdict alone (effective 100% in the spending or five-hour bucket), and dead auth, which the rows call `login needed` because it is a login to fix rather than a window to wait out; the selector reads their union where all it needs is "cannot serve". The two keys above the budget are the contract's only softenings and neither of them is a skip. The **five-hour deferral** ranks a candidate reading `FIVE_HOUR_DEFER_PCT` (80) or more behind every candidate below it, whatever the budgets say, and tags its vendor row `5h!`, because an account that walls after the first task is the wrong no-brainer answer — an unmeasured five-hour window never defers, and grok, which measures no five-hour bucket, can never fire it. A **fresh claim** ranks an account another caller took within the claim TTL behind every unclaimed one (below). Both stay soft: a deferred or claimed account is still the answer once nothing above it remains. `main` is not a ranking key on any vendor — what keeps a base account from being spent by workers is the pool-side shield, which reaches the picker as an ordinary pool exclusion with no rule of its own. The one write into `~/.claude/worker-model` is a pinned account that walled on data this run calls fresh: the pin is removed outright (`pin X hit its wall — cleared` on stderr), because it is pinned to be spent; every other lapse leaves it standing. The wall that ends it is one that ARRIVED after the pin — pinning an account already at 100% asks for the window after that wall, so the vendor CLI records its horizon beside the pin (`<vendor>_profile_wall=<epoch>`, written and stripped with the pin) and a wall standing no longer than the record clears nothing; a pin with no such line is ended by the first wall as before. `worker-pick --account claudeb|codex|gemini|grok` is the machine-readable face of the same selection for callers that must pick an account themselves (`claudeb`'s headless routing, `review-bench`'s per-rater choice): one bare account name on stdout and nothing else, exit 3 only when no candidate remains; `--fable` asks the same formula about the fable bucket and its reset. `--role workers|reviewers|chat` says which role is asking: `workers` is the default and the only one the pin serves, `reviewers` is a rater, and `chat` is where Egor's own session should move next (`bin/chats`, the `*` in `claudeb status`) — it has no `<vendor>_chat` switch, and the session account stands there as an ordinary candidate like everywhere else. `--exclude name[,name...]` drops accounts from that one query, which is how a caller that just watched an account wall asks for the next one; running out of candidates is exit 3 / `ALL WALLED, ask Egor`, not a quieter answer. `--claim` — valid only with `--account`, and passed only by a caller about to launch — records the answer in the claims ledger (`share/worker-claims.sh`: one empty marker per claim under `~/.cache/worker-claims/<vendor>/<account>`, its mtime the entire state, `WORKER_CLAIMS_TTL` default 600s), which is the whole mechanism that keeps parallel launches off one account; a query that cannot read the ledger routes as if there were no claims. ## The 429 taxonomy (do not conflate these)

Transient upstream 429s are still real. They are passed to the Claude CLI, which owns its
retry behavior; this project no longer turns them into account walls, holds, or locally
generated 503 responses.

1. **OAuth token-endpoint 429** — `bin/claudeb`'s `oauth_refresh()` backs off only the direct-refresh path (`oauth_backoff_until`); the warm/heal path uses its separate `oauth_heal_backoff_until` state.
2. **Warm-probe failure classification** (`bin/claudeb`'s `heal_one()`/`warm_accounts()`) — a failed zero-cost warm probe is classified into a cause (`timeout`, `warm-429`, `usage-probe-failed`, `warm-failed` = capacity-shaped upstream weather, vs. `needs-relogin`/`profile-setup` = auth-shaped), persisted as `warm_cause` in `oauth-attempts.json`. Capacity-shaped failures leave valid snapshots untouched and do not stamp auth expiry.

**Robot curl refresh is permanently off** (shared-invariants row f; the marker that used to hold it is gone, and there is no switch to turn it back on) — the direct curl POST to the OAuth token endpoint is vendor-blocked for automation, so `oauth_refresh()` short-circuits with rc `76` on every path that does not carry the menu's explicit user signal. The free CLI warm still runs for automation; only its direct curl fallback is skipped. `CLAUDEB_WARM_USER_EXPLICIT=true` is set by every user menu refresh (global `Refresh`, global `Refresh + Start Windows`, per-account Hard refresh, and `r` in the status TUI) and exempts that whole invocation — its warm, heal, and direct curl-refresh steps all run as before. Every token-endpoint-relevant event — real attempts and outcomes, warm outcomes, adoptions, and robot skips — is journaled append-only to `~/.claude-profiles/.claudeb/token-attempts.jsonl` (`{ts,account,kind,outcome,http,pid}`), with `"user":true` added only for events in a user-explicit invocation; a `robot-skip` outcome means the guard held that path (deliberate evidence, not an error). A dark account under a robot refresh renders its stale-cause as `robot curl refresh off (manual refresh only) — revive path active`; a user-explicit failure, and any cause recorded by the revive path itself (`warm_kind: "revive"` in `oauth-attempts.json`), instead name the observed token-refresh, warm, usage-probe, or timeout outcome — the robot banner never masks the escalating refresh's own verdict.

**Rotating a dark account** — `claudeb revive <name>` is the sanctioned replacement for the blocked curl refresh and is the one rotation a robot path may drive: `bin/claude-session-driver` runs one interactive `claudeb profile <name>` session under a PTY (no prompt, no model tokens, only `/exit` and, if that is ignored, two Ctrl-C), and the rotated token then feeds the ordinary free usage probe so `five_hour`, `seven_day` and `fable` all land in `limits/<name>.json`. Driver exits: 0 rotated, 4 the account needs a human login (revive marks `auth_needed`), 5 timeout or other failure. Revive itself also exits 4 when the usage probe answers 401/403 to a token it just rotated — a live token being rejected is the endpoint's verdict, so the flag is written rather than the account retried. Session transcripts go to `~/.claude-profiles/.claudeb/session-logs/<name>.log` in the warm-log format; rotation evidence is journaled to `token-attempts.jsonl` under kinds `session` and `revive`. An unknown account is refused without driving anything, and so is an `auth_needed` account whose token is still missing or expired; an out-of-pool account is not refused at all — that toggle is spend consent (shared-invariants q) — and `claudeb token-fresh <name>` is the read-only question about the same token this path branches on (exit 0 live, 1 expired, 2 unknown account); once the human has logged in, the live token lets revive through to the probe, whose merge clears the flag.

## Reading `~/.llm-limits.json` as an LLM

Treat `stale`, `expired`, `as_of`, and `effective_pct` as the data-honesty contract. Never infer current availability from raw `used_pct` alone: keep it as provenance, check the bucket's `resets_at` against the current time, and refresh before acting on an old or rolled-over frame.

## Display contract (hammerspoon/llm-limits.lua)

- **Gray** = stale bucket (`.stale == true`), or the collector's own `.expired == true`, or the renderer's own render-time check that `resets_at` has already passed (>60s clock-skew tolerance) — this last case covers a window whose reset landed between collects, before the stored `expired` flag catches up. Missing or false `.stale`/`.expired` alone is not gray; a future `resets_at` is never gray.
- **Reset time** = the collector converts raw zero, empty, absent, and 1970-era reset placeholders to `resets_at: null`; Lua renders null/absent as `–`. Any real reset timestamp, including one the renderer now treats as past-due, remains visible as its actual clock time.
- **Refresh failure** = vendor `refresh_errors` is `[{account,class,cause,at}]` from the collector (classification in `classify_cause`); `refresh_error` `{cause,at}` is derived from that list for one release. `needs_user_entry:true` only when every entry requires a human account entry. The menu renders one dim `⚠ <account|vendor>: <class> · <age>` row per entry inside that vendor section (under the account, or under the vendor header when vendor-wide), with the raw cause in a submenu, and persists across passive menu-open collects until that vendor refresh succeeds. An entry whose account is off the roster is not rendered and is dropped at the next write. Entry-only errors do not raise the global menubar `⚠`; real faults and mixed errors do. The affected account carries the same flag and renders `!` beside its data age. Top-level `refresh_error` keeps the base shape and renders as a red top row; it is reserved for no available vendor data or a full refresh with zero successful vendors. The menu also renders an observed nonzero collector exit as a red runtime error when no cache-level global error exists; any later successful task, including a passive collect, clears that runtime residue after reading a valid cache without a top-level error.
- **Red** = usage warning colors only. Claude rotation metadata is computed locally from the enabled flag and snapshot auth status; wall metadata no longer exists.
- **Fable early warning** = when an `fb` bucket is at least 80%, only its usage-bar substring is red. The rest of the row retains its normal or stale color.
- **Table model and markers** = every row has first-class `5H%`/`WK%`/`FB%` and matching reset columns, plus `AGE`, `ROT`, `CR`, and `STATUS`; there is no `NOTE`. Rows without Fable render `-`. A `~` suffix marks a stale bucket and `!` marks an expired bucket; both may appear, and displayed percentages remain raw `used_pct` values. `AGE` comes from that row's account/vendor `as_of`, which is the oldest timestamp among windows with a numeric `used_pct`; absent and null-valued windows do not participate (`2m`, `1h48m`, and similar).
- **Table rotation and credits** = `ROT` is `off` when the account is out of its vendor's worker pool (all four vendors) — a spend verdict only, never a refresh one: the heartbeat reads an out-of-pool account's usage like any other, `limit-5h`/`limit-weekly`/`fb:limit-fable` when a local effective percentage reaches 100, otherwise `-`. Claude `rotation.usable.general` and `.fable` remain available to worker-pick; the account projection also exposes their general hard gate as `blocked`. `CR` renders a numeric `reset_credits` as `↻N` for whichever vendor published one, including `↻0` — Codex reads it out of its usage payload, grok through `prod_mc_billing.ConsumerUiSvc/GetRemainingResets` — and both also carry `reset_credits_expires_at`, the instant the soonest still-spendable grant lapses. The menubar row shows the count and the usual data age and nothing else; the expiry rides the submenu's `Redeem usage reset · <when>` action, identically worded for every vendor.
- **Table status** = `STATUS` is `login needed` for a Codex account with `auth_needed == true`, a Claude account with a present non-`ok` `auth.status`, or a logged-out Gemini profile (`auth_needed == true`, collector-owned status `login needed`); a Grok account with `auth.status=expired` is not — the CLI refreshes it, so the row renders `-`, while `needs_login` is dead auth and is `login needed`; other unavailable rows show their collector-owned status text; all other rows render `-`. A logged-out Gemini profile records its own `refresh_error` cause from the agy helper; a successful profile refresh clears it without changing sibling snapshots.
- **Gemini account rows** = every non-removed profile gets its own account, 5h, and weekly rows; the compact single row survives only for a store without an accounts array. A logged-out profile uses the shared `Log in…`/`Hard refresh`/`Remove <name>` submenu; login opens `geminib profile <name>`, hard refresh targets `gemini/<name>`, and `main` is removed like any other name.
- **Grok account rows** = every profile gets its own account row and a WEEKLY row, and nothing else: the plan measures one pooled weekly window, so a five-hour cell must never appear and an absent one is never rendered as `?`/`nil`. Where the billing answer carried a Grok Build percentage the weekly row carries it as a `  build N%` detail suffix beside the pooled number — the pooled window is what is spent, the Build share is only which product spent it. A profile with no usable login renders the shared `login needed` row with the `Log in…`/`Hard refresh`/`Remove <name>` submenu, like a logged-out Gemini profile.
- **Plain model** = each line mirrors the table's labeled 5h/weekly/Fable values and resets, age, rotation, credits, and status. The same `~`/`!` markers apply, expired values are never rewritten to zero, and an unavailable vendor's `last_wall` is appended when present.
- **●** marks the current account from the account block's collector-owned `is_current` flag.
- **In-flight indicator** = passive menu-open collects never render an indicator. Verified-live explicit, hard, and start-window tasks share one registry and prefix the normal menubar title with `⟳ ` immediately; standing vendor or global errors prefix it with `⚠ ` when no explicit task is active. Resume-timer text remains visible. Ordinary entries use a 360s cleanup budget and start-window entries 1200s, but an over-budget task that still reports running remains registered and suppresses duplicates; only a verifiably-dead entry is removed.
- **Checkbox ("In pool")** appears on every logged-in real account row of all four vendors (`enabled` = neither explicitly excluded nor shielded; the separate `shielded` boolean says which of the two it is) — toggling it calls that vendor's own `enable`/`disable`, and enabling a shielded main overrides the shield until its week rolls over. It consents to SPEND and nothing else: an excluded account is still refreshed by the heartbeat and `claudeb revive` still takes it. The compact sole-account Gemini row carries it too — no membership is immutable. A **login-needed** row deliberately has none: pool membership on it would claim an availability the account does not have; the stored exclusion survives and reappears once it is logged back in. An explicit/pinned Claude profile entry is not part of `claudeb-store` and so still has no checkbox.
- **"Pin for workers"** on each logged-in account row sets/clears that vendor's `<vendor>_profile=` pin via `<vendor>b use` (`use --clear` when already pinned); a login-needed row offers it only when that account is currently pinned, so a stale pin can always be removed. The row marker `●` means the pin and nothing else — solid when honourable, gray when the pin exists but is lapsed (logged out, removed, blocked, or at limit). A pin absent from the rendered account rows gets a gray clear-only row, so removed profiles and stale configuration remain visible. Pool exclusion alone does not hide a pin.

## Claude Code statusline hooks

`statusline-workdir-hook.sh` (PostToolUse matcher
`Bash|Edit|Write|NotebookEdit|Read|EnterWorktree|ExitWorktree`, plus a PreToolUse matcher
`Bash|Task|Agent` — `Bash` there only to snapshot the worktree list a `git worktree add` is
diffed against, so a PreToolUse registration without it kills that path whole) records the git toplevel a session actually works in; the status line shows it with a
magenta `»` marker when it differs from the launch repo. That is the only question it answers:
which changed paths are THIS chat's work is the commit journal's (`<common-dir>/claude-commit-journal`
— one ledger per checkout family, wherever in it the write happened —
`<session>TAB<epoch>TAB<path>`), and the `touched-<session_id>` file this hook used to write beside
it had no reader left once the review segment became the review gate's mouthpiece.
Rules:
- Events carrying `agent_id`/`agent_type` report the PARENT `session_id`, so a subagent's Bash,
  Read, dispatch (and every non-write tool) is ignored — a worker's stray `cd` must never retarget
  the parent's display, and an Explore agent reads across every repo it can reach. Its
  Edit/Write/NotebookEdit events do count, but only through the sustained-work run
  below: three writes in a row into the same other toplevel, in ANY home (worktree or not),
  since a worker starts where it was dispatched, not where the session lives. With no state file
  at all a subagent write adopts its toplevel at once, like any other event.
- Task/Agent (the dispatch tool, named either way depending on harness version) is heard on
  PreToolUse only — in orchestrator mode the worker's edits happen in a process that reports
  nothing, so the brief is the only signal, and hearing the PostToolUse replay too would count one
  dispatch twice. The first ten `/`-rooted tokens of `tool_input.prompt` + `.description` are
  scanned and the FIRST that clears the exclusions and `cd`s into a git repo wins (briefs name the
  worker's cwd early; a file path does not resolve). It is write-grade evidence from the session:
  immediate on a non-worktree home, through the run against a worktree pin.
- Read (main session only, `file_path` dirname'd) is the weakest evidence and never retargets at
  once: three consecutive reads into the same other toplevel, in ANY home. With no state file it is
  ignored — a home is seeded by SessionStart or adopted by a write, never established by a lookup —
  and a read back home neither rewrites the home nor clears a run in progress, but does interrupt
  it (its toplevel is appended onto an existing run, never onto an empty one), since without that
  the three need not be consecutive and scattered lookups alone would move the home.
- Bash: the LAST `cd`/`git -C` in the command wins (`;`, `&`, `|`, `&&`, `||`, `(`-subshell, and
  newline-separated all match; `(cd /path && cmd)` is the form the cd-guard hook prescribes).
  A winning cd that sits after `(` is a subshell one and dies with the command — the session's
  own cwd never moves — so it retargets only through the same sustained-work run: three
  consecutive subshell cds into the SAME toplevel (a worktree-pinned home ignores them entirely).
  A persistent `cd`/`pushd`, and `git -C <dir>`, still retarget on the first one, and the
  persistent cd is the one thing besides sustained work that breaks a worktree pin: cd-guard
  denies every persistent cd a session has not unlocked, so one that arrives is a deliberate
  move. `git -C <dir>` counts only when followed by a mutating
  subcommand (worktree/checkout/switch/commit/merge/rebase/cherry-pick/revert/restore/stash/
  am/reset/pull); read-only `git -C ... status/log/diff` never retargets.
- A Bash `git worktree add` is the one command also heard on PreToolUse, where it snapshots the
  worktree lists of the `-C` dir, the session cwd and the current home into
  `workdir-<sid>.wtadd`; the PostToolUse diff of that union names the created path (the command
  text cannot — `... worktree add $N` expands in the shell), and exactly one new path retargets,
  a failed or ambiguous add nothing. No snapshot falls back to the parsed token.
- EnterWorktree records the toplevel of the `worktree at <absolute path>` in `.tool_response`
  (string or object); ExitWorktree deletes the session's state file. tmp/system/`~/.claude*`/
  node_modules paths are excluded; records older than 7 days are pruned.
- Also registered for SessionStart: `source` `startup`/`resume`/`clear` clears the session's
  workdir state file and re-seeds it from the starting cwd's git toplevel (without a seed the
  first cd anywhere would adopt THAT dir as home, and worktree stickiness can only protect a
  home that already exists); `resume` is the one exception — ANY home that still resolves as its
  own git toplevel is kept, worktree or main checkout alike, because the resume cwd is where the
  chat was relaunched (usually the main checkout), not where its work lives; a surviving
  directory is not enough (a worktree without its `.git` link, or any subdirectory, resolves up
  into the owning checkout, whose branch would then be shown as the workspace); `compact` keeps it — the shell and its
  cwd survive `/compact`. This runs before the agent filter on purpose: `agent_type` on
  SessionStart means a top-level `claude --agent` session, not a subagent.
The statusline itself unlinks a state file that no longer points at a git dir.

State files are stored at:
- `~/.cache/claude-statusline/workdir-<session_id>`
- `~/.cache/claude-worker-tags/<agent_id>`

`worker-tag-hook.sh` derives the actual relay account/model/effort from Codex, claudeb, or `geminib profile`
launch commands and prefixes the tag onto later Bash activity descriptions for `codex-worker`,
`claudeb-worker`, and `gemini-worker` agents. It exits
silently for any `hook_event_name` other than PreToolUse (its rewrite payload hardcodes
`hookEventName: "PreToolUse"`, so a mis-registration must be a no-op).

`limits-triage-nudge.sh` (PostToolUse matcher `Bash`) scans Bash tool output for a limit-shaped
pattern (`no available accounts`, `API Error: 503/529`, `usage limit`, `overloaded`,
`anthropic-ratelimit`, `CLAUDEB_USAGE_LIMIT`, `claudeb ... timed out`) alongside a
claude/claudeb/anthropic/fable context word in the same output, and nudges the session to run
`llm-limits --table --no-write` instead of theorizing. Dedup: one nudge per session per
15 minutes, state in `/tmp/claude-limits-triage-nudge-<session_id>`.

To disable any of these hooks, remove its entry from `hooks.PostToolUse` or `hooks.PreToolUse` in
`~/.claude/settings.json`.

Debug workdir tracking (a mutating `git -C` subcommand or a `cd` is required to record):
`jq -cn --arg dir "$PWD" '{hook_event_name:"PostToolUse",tool_name:"Bash",session_id:"debug",cwd:$dir,tool_input:{command:("cd " + ($dir | @sh))}}' | ~/.claude/hooks/statusline-workdir-hook.sh; cat ~/.cache/claude-statusline/workdir-debug`
