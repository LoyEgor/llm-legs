# Diagnostics: llm-legs multi-account/limits ecosystem

Symptom → cause → fix for anything llm-legs runs.

## System map

- `llm-limits.sh` — read-only collector, writes `~/.llm-limits.json` (schema `{schema, fetched_at, vendors}`). A failed vendor refresh preserves its last valid buckets and records `vendors.<vendor>.refresh_error` as `{cause,at}` with optional `needs_user_entry:true`; passive collects preserve that outcome, and the next successful refresh of that vendor clears it. A full refresh with no successful vendor records the same base shape at top-level `refresh_error` and exits nonzero; partial and targeted failures exit zero. `--refresh` polls free usage endpoints; `--start-windows` is the only paid path (never call from scripts). `--table`/`--plain`/`--json` control rendering; piped output defaults to JSON.
- `bin/llm-refresh` — the escalating refresh driver behind the `com.llm-refresh` launchd heartbeat (`~/.local/libexec/llm-refresh-heartbeat` wrapper, 300s StartInterval; `bin/llm-refresh install-agent`/`uninstall-agent`). Per-vendor cadence state in `~/.llm-limits-refresh.state`, one JSONL line per vendor per due tick in `~/.llm-limits-refresh.jsonl` (`outcome` ∈ `fresh-passive|refreshed|partial|pushback|error|timed-out`, plus OpenCode's own three below: `dormant|walled|reopened`; `partial` names the accounts still stale, and accounts no refresh can help — removed or auth-dead, except a Gemini login verdict 30 min old, which is re-probed because agy's keychain timeout forges one; worker-pool membership is spend consent and never gates a refresh — are never targeted and are listed as `unrefreshable:` in the detail instead of pinning the vendor at `partial`). Every vendor starts at 30 min on one ladder (15→22→30→45→60): a 429/rate-limit signal — from collector stderr or the store's `refresh_error` fields — loosens one rung, 24h with none tightens one rung, so per-vendor cadences diverge only from observed pushback, never by assumption; `llm-refresh reset-cadence [vendor …]` puts a vendor back on the base rung under the tick lock, the only supported way down for a rung climbed on a signal that turns out to have been misread (never hand-edit the state file — a tick may hold its lock). What counts as pushback is a VERDICT about the read (`429`, `too many requests`, `rate limit exceeded`, `rate-limited`, `RESOURCE_EXHAUSTED`) and never the NAME of the thing being read: the codex usage RPC calls itself `rateLimits/read` and words every failure `failed to fetch codex rate limits: <real cause>`, so a bare `rate limit` match read every codex probe failure — an auth-dead account, a 402 workspace, a timeout — as pushback. An account's own spent window (`usage limit`, `quota exceeded`, `out of credits`) is bucket state and VETOES a pushback verdict on the same line — including a 429 whose body restates the wall — so the journal records `usage wall, not endpoint pushback: <excerpt>` and the cadence stands, a wall being exactly when the numbers matter most. Every `pushback` line carries a bounded excerpt of the text that matched, printable-ASCII only and stripped of anything token-shaped (`LLM_LIMITS_REFRESH_EXCERPT_MAX`), because `~/.llm-limits-refresh.log` is truncated per run and a rung with nothing behind it but "a 429 or rate-limit signal" is a rung nobody can audit. Step 0 is one passive collect shared across due vendors; step 1 runs ONE `--refresh-account <vendor>/<a>,<b>,…` per vendor naming every still-stale account (gemini adds its login re-checks to the same call; the collector reads gemini's accounts in parallel, codex's in parallel threads of `codex-quota.py --profile …`, grok's in one helper call) — a collector call costs minutes under load — except Claude, whose token endpoint is vendor-blocked: its step 1 splits the stale accounts by what `claudeb token-fresh <account>` says. A token that still carries a request needs no session — `claudeb revive` on it is one usage-endpoint GET — so EVERY such account is revived in the same tick, under the tick lock, `timeout`-guarded at `LLM_LIMITS_REFRESH_PROBE_TIMEOUT` and with no attempt stamp, since a live chat rotates its own token and must never wait for a session slot. Only an expired token needs `claudeb revive <account>` as a real session, and that is still one per tick (the least recently attempted of the expired accounts — every session attempt, success or failure, stamps `vendors.claude.attempts.<account>` in the state file, so a persistently failing account rotates out of the way instead of owning every tick; ties go to the stalest — `timeout`-guarded at `LLM_LIMITS_REFRESH_REVIVE_TIMEOUT`; the rest wait for the next tick, and the detail says so, naming what it `probed:` and what it opened a `session:` for; Claude's reserved `main`/`-` names are `unrefreshable` too, since no revive can take them), followed by a collect so the rotated snapshot reaches the merged store. That interactive session holds no tick lock: the attempt stamp is persisted to the state file BEFORE the lock is handed back — otherwise a tick starting meanwhile picks the same account and opens a second session on it — the state is re-read from the file after the lock is reacquired, since whoever held it in between owns what is on disk, and a tick that cannot get the lock back stops there instead of racing the new holder through the remaining vendors. A revive that needs a human login — a login screen, or a usage 401/403 against a token it just rotated — makes that account `unrefreshable` and journals `error` — never `pushback`, which is reserved for a real 429 from the session. Tick lock `<state>.lock`, broken by holder liveness: a dead holder at once, a live one never until its ceiling, an ownerless directory after its grace. OpenCode is the one inverted vendor: the Go plan publishes no usage endpoint, so there is nothing to collect passively and its only probe is a real completion. With no walled account in `~/.llm-limits.json` it is dormant — outcome `dormant`, zero requests, no passive collect started on its account — because every real call already records its own outcome (invariant `ai`). A standing wall is probed one `opencode-go wall-check` per walled account, which is free while the window is shut, and the tick lock is handed back while it is out so a wedged gateway holds no other vendor's tick. The probe answers in three states and the journal keeps them apart: outcome `walled` when the gateway repeats the 429, `reopened` when the plan SERVES the completion (the only thing that ends a wall, recorded as that account's served stamp — no record is ever dropped), and `dormant` when the wall went between the read and the request, so nothing was sent; the first two re-collect, so the rows every surface reads follow the probe. Whether a wall stands it asks the collector and never the record (invariant `al`). Its rung is read off the stated reset — day-granular, so approximate: within an hour of it, past it, or with none stated the ladder tightens and keeps probing, since only a served request ends a wall.
- `share/store-lock.sh` — mkdir-based lock serializing every read-merge-write of `~/.llm-limits.json`: `llm-limits.sh` re-reads previous state INSIDE the lock right before the jq merge, network stays outside, the write is an atomic `mv`, pid-owned with a rename-aside break by holder liveness — a dead holder at once, a live one never until its ceiling, an ownerless directory after its grace (both env-overridable; only the owner may release), skipped entirely under `--no-write`.
- `bin/claudeb` — account prober/launcher. Snapshots per account in `~/.claude-profiles/.claudeb/limits/<name>.json`:
  ```json
  {"five_hour":{"used_percentage":6,"resets_at":1784044800,"as_of":1784031056,"origin":"usage"},
   "seven_day":{...}, "fable":{...}, "auth":{"status":"ok","checked_at":1784031056}}
  ```
  `origin` ∈ `usage|headers|cached`. `auth.status` is only ever `"ok"` or `"expired"` (never `needs re-login`/`auth_needed` — the first is a free-text `cause`, the second a separate login-needed flag).
  **Usage reset (Claude Code's `cedar_ember` program).** The usage GET is `https://api.anthropic.com/api/oauth/usage?cedar_ember=1` — the plain body plus a `cedar_ember` object (`eligible`, `ineligible_reason`, `grants[]` of `{id, resets_left, ends_at, paused, usable_now, use_requires_limit, clears[]…}`, `next_grant_id`, `cooldown_until`), null on an account with no program; never add `skip_spend=1`, it drops `.spend`. `merge_usage` publishes `reset_credits` (sum of `resets_left` over unpaused grants whose `ends_at` is null or ahead; `0` for a program with none), `reset_credits_expires_at` (soonest such `ends_at`) and `reset_credits_as_of`, and deletes all three when `cedar_ember` is null — an unmeasured count is never rendered; `merge_headers` leaves them alone. The write is `POST /api/organizations/<.oauthAccount.organizationUuid of the profile's .claude.json>/reset_rate_limits` with `{"program":"cedar_ember","grant_id","request_id"}` (reply `result` ∈ `reset|already_used|not_limited|cooldown|ineligible|unavailable`), spelled once in `share/claude_resets.py` and reached only through `bin/llm-reset-redeem claude/<account>` (the menubar's confirmed click, or an armed account's weekly wall — see the grok paragraph's auto-redeem): keychain token only, never refreshed there (401/403 → exit 3), grant = `next_grant_id` else the soonest `ends_at`, `request_id` = uuid5 of target/grant/`resets_left` so a re-click after a lost reply answers `already_used`, and a timeout/429/5xx is never retried. Test seam `CLAUDE_RESETS_ENDPOINT`. A redeemed reset writes `limits/<account>.reset-at` (epoch) before the re-read: the reset lowers the week without moving its `resets_at`, so for 8 days `bin/statusline.sh` merges a reading into that account only when it followed spend after the marker, or an idle chat's pre-reset 100 re-walls the account until the week ends.
  **Account existence is one set** (shared-invariants row x): `account_names` unions `tokens/`, `limits/*.json`, and the `~/.claude-profiles/<name>` dirs (reserved `main`/`-` filtered), and every verb — `status`, `enable`/`disable`, `warm`, probes, `use` pin validation — consults it, so a keychain-only browser login (no setup token) is as real as an `add`ed account. Account birth (`add`, first-launch profile create) fires a detached targeted collector refresh and removal fires a passive collect (`share/account-announce.sh`), so the menu follows without a manual refresh.
  Two independent OAuth-heal paths sharing `oauth-attempts.json`: **warm** (drives the real `claude` CLI's own OAuth rotation, zero-cost — a token-endpoint 429/failed record must never gate it) and **direct refresh** (claudeb's own curl POST to the token endpoint, `oauth_refresh()`). `.claudeb-state` = current account name (single line); `disabled` = one excluded-account name per line, absent file = all enabled — this is the **worker pool**, and all four vendors now share it (`share/worker-pool.sh`, one file per vendor: `~/.claude-profiles/.claudeb/disabled`, `~/.codex-profiles/.codexb/disabled`, `~/.gemini-profiles/.geminib/disabled`, `~/.grok-profiles/.grokb/disabled`; the dot-directory keeps it outside the profile enumerators' `*` glob). Exclusion is a WALL for every headless run: `worker-pick` and `codexb pick` skip the account, and `claudeb … -p`, `codexb <name> exec`, `geminib profile … --print`, `grokb profile … --prompt-file` and `worker-run start --account <name>` refuse it outright — only the vendor pin in `~/.claude/worker-model` overrides. An interactive session is the user and is never gated, so any member may go out, the last one included; an empty pool then answers `every <vendor> account is out of the worker pool` and `worker-run` reports `OUTCOME: <VENDOR>_UNAVAILABLE`, never a usage limit. `claudeb enable|disable`, `codexb enable|disable`, `geminib enable|disable`, `grokb enable|disable`; the state is visible in each tool's own `list`/`status` (`(out of pool)`), in the table's `ROT` column (`off`), and as the menu checkbox.
  Entry points, and the whole reason there is no daemon: an **interactive** run must name a profile (`claudeb profile <name>`; bare `claudeb` and any argument list without `-p`/`--print` print the profile list and exit 2), while a **headless** run (`-p`/`--print`, i.e. a program calling claudeb — find-truth, usage-ai-report, any script) takes its account from `worker-pick --account claudeb` and then runs exactly the `claudeb profile <acct> …` path — in-process, so there is no second `claudeb` in the process tree. That path has no wall, no hold, and no retry: nothing selectable exits immediately with the query's own **3** (a caller choosing between "retry after the reset" and "this is misconfigured" needs those apart), a missing or unusable `worker-pick` exits 2, and no request is ever parked until it becomes a 503. `CLAUDEB_WORKER_PICK` overrides the binary (a sibling of the resolved script wins over `PATH`, so both halves of the query contract come from one checkout). Headless runs never restamp `.claudeb-state`. The `*` in `status`/`accounts` is a routing answer and not the last account launched: it is `worker-pick --account claudeb --role chat` (the pool toggle, the pin and the workers switches are all ignored — they steer delegated work, never the account Egor talks to; an account out of the pool shows `workers off` beside its star), and where that answers nothing no row carries it; the shared `share/account-status-tui.sh` picker initially selects the starred row (otherwise the first row), and Enter launches the selected profile. `.claudeb-state` keeps its own meaning — the last profile launched, which `bin/chats`, `bin/chat-find` and `workflow-burn-gate.sh` read. `claudeb use <name>` writes the same `claudeb_profile=` pin in `~/.claude/worker-model` that `/worker claudeb <name>` sets — the pin every consumer already reads (worker-pick routing, `worker-limit-gate.sh`, the statusline `w:cb @`) — leaving `worker=` alone so naming an account cannot also re-route work to another vendor; `use` with no name prints the pin, `use --clear` removes it, an unroutable name is refused, and an out-of-pool account is accepted with a note that the direct pin overrides automatic pool exclusion.
- `bin/codexb` + `codex-quota.py` — same idea for Codex CLI, no proxy: per-account `CODEX_HOME` under `~/.codex-profiles/<name>`; quota via zero-spend app-server RPC (`account/rateLimits/read`), cached in `~/.llm-limits-codex.json`. The JSON-RPC session that carries every such call is `share/codex_appserver.py`, the one place a `codex app-server` process is spawned. The same payload's `rateLimitResetCredits` gives `reset_credits` (`availableCount`) and `reset_credits_expires_at` (the soonest `expiresAt` among the credits still `available`); the write side is `account/rateLimitResetCredit/consume` — `creditId` plus an `idempotencyKey`, both refused empty — reached only through `bin/llm-reset-redeem codex/<account>`, which the menubar fires behind a confirmation and nothing automated calls unless Egor armed that account (auto-redeem, below). `codexb status` on a TTY uses the same `share/account-status-tui.sh` picker as claudeb, with worker-pick’s chat answer starred and initially selected; Enter there opens Claude Code on the selected account through `claudegpt p <name> --model astra` (`codexb_status_model`, the same alias `share/chat_resume.py` pins for a chat switch — `docs/shared-invariants.md` row `cj`; `CODEXB_CLAUDEGPT_CMD` overrides the launcher; no launcher is exit 2, never a silent `codex`). Both pickers are vendor-scoped — `codexb status` lists the OpenAI accounts and `claudeb status` the Anthropic ones, never each other's — while every other `codexb` verb — `profile`/`p`/`run`, `<name> exec`, `login` — stays native Codex, and non-TTY output remains one line per account (`com: Logged in ... | 5H ... | WEEKLY ...`) with `auth_needed`/`Not logged in` and no usage buckets for an account needing login.
- `bin/geminib` + `agy-quota.py` — Antigravity profiles without touching the live login: `main` uses the real `HOME` and is removed like any profile — `geminib remove main` leaves only the marker `~/.llm-limits-gemini.json.removed`, the same file the menubar's `llm-limits.sh --gemini-remove` writes (delete it to bring `main` back; nothing else ever clears it); named profiles run with `HOME=~/.gemini-profiles/<name>`. There is no supported narrower profile flag or environment variable. Shared Gemini settings and Playwright driver/browser caches are symlinked from the base HOME while authentication remains isolated. `geminib profile <name>` creates and launches a profile for its one-time Google login; `list`/`status` probe each profile independently. Main quota stays in `~/.llm-limits-gemini.json`; named caches live in `~/.llm-limits-gemini/<name>.json`.
- `bin/grokb` + `grok-quota.py` — the same idea for the xAI Grok Build CLI (SuperGrok): per-account `GROK_HOME` under `~/.grok-profiles/<name>` — a complete jail (auth, config, sessions, memory, plugins) — with `main` meaning the real `~/.grok`, which carries no login and therefore no fallback: `grokb add <name>` runs `GROK_HOME=<profile> grok login --device-auth` and every headless launch (`grokb profile|p|run <name> …`, `grokb <name> exec …`) also exports `GROK_CLAUDE_MCPS_ENABLED=0`, `GROK_CLAUDE_SKILLS_ENABLED=0`, `GROK_DISABLE_AUTOUPDATER=1` and `GROK_WORKER=1` (the marker `worker-git-guard.sh` keys a worker's branch discipline on, as `CLAUDEB_WORKER=1` does for claudeb). `grok-quota.py` reads each profile's `auth.json` READ-ONLY — it never refreshes a token — and asks `GET https://cli-chat-proxy.grok.com/v1/billing?format=credits` (`Authorization: Bearer <key>`, `X-XAI-Token-Auth: xai-grok-cli`, `x-userid`), zero tokens; cache `~/.llm-limits-grok.json`, fixture seam `LLM_LIMITS_GROK_QUOTA`. `vendors.grok` in the store is **weekly-only** — the plan pools Chat/Imagine/Build into one weekly window, so there is no `five_hour` bucket and no surface may invent one — plus optional `build_pct` (`productUsage[PRODUCT_GROK_BUILD]`) and a per-account `auth.status` of `ok|needs_login|expired`. `expired` is a live candidate, not dead auth: the CLI refreshes an expired access token itself, so `worker-pick` ranks such an account behind every signed-in one (`auth_late`) instead of walling it, while `needs_login` has no refresh token left and IS dead auth. `worker-run start grok` launches `env GROK_MEMORY=0 grokb profile <acct> --prompt-file … --output-format streaming-json --always-approve --cwd <dir> --no-subagents --reasoning-effort <e>` with NO turn cap — the wall-clock deadline is the runaway guard here as it is for every other vendor, and `WORKER_RUN_GROK_MAX_TURNS=<n>` is the opt-in that puts `--max-turns` back — takes the session id and usage off the stream's terminal `end` event, resumes with `-r <id>` (`-s` only ever CREATES), and reads a run's files from `$GROK_HOME/sessions/*/<id>/updates.jsonl` verified against the workdir the session recorded. Only the PERSISTENT wall wording counts as a limit (`hit the rate limit/credit limit for your plan`, `subscription:free-usage-exhausted`, 402, `run out of credits`, `you['’]ve reached your free Grok Build usage limit for now`); the CLI folds 429/5xx capacity weather into the same internal class and that is never a wall. `bin/grok-image` is the leg's image generator, carrying `gemini-image`'s flags: the CLI's `image_gen` sends `resolution=1k` and answers **JPEG only** (1024x1024 at 1:1, 1280x720 at 16:9 — live-measured), so there is no native alpha and `--transparent` is the shared chroma-key path, not a transparent generation. `aspect_ratio` is its one knob and takes `1:1|16:9|9:16|3:2|2:3`; `4:3`/`3:4` belong to `image_edit`, which a run reaches only through `--ref`, and are refused before anything is sent — a single reference makes `image_edit` ignore the ratio entirely and match the source image instead. The reset consumable grok.com's Usage panel calls "Usage Limit Reset" is a second, independent read: `share/grok_resets.py` speaks gRPC-web+proto to `POST https://grok.com/prod_mc_billing.ConsumerUiSvc/GetRemainingResets` with the same bearer (base URL behind `GROK_RESETS_ENDPOINT`, its own `GROK_RESETS_TIMEOUT`), and `grok-quota.py` publishes `reset_credits` (the token count) plus `reset_credits_expires_at` (the earliest `validity_end`) — but only on a successful call, so a failure leaves both keys absent rather than rendering a count nobody measured, and it can neither fail nor delay the usage read. `bin/llm-reset-redeem <vendor>/<account>` is the write side for every vendor (`RedeemReset` here), reachable from the menubar's per-account "Redeem usage reset" item behind a confirmation: it spends a one-per-period consumable, so nothing automated calls it unless Egor armed that account. **Auto-redeem** is that arm, and nothing but his own word sets it: «сделай ресет <account>» (any shared «сделай» verb form; claude-setup's `reset` word family, whose intake calls `arm_words` here in-process with the prompt it was handed and prints `⚡ reset → <vendor>/<account>, …` — a bare name held by one redeem vendor arms it, one held by several arms nothing and says `<name>: which vendor? …` (it would spend a reset he did not mean), an unknown name arms nothing and says `<name>: no such account`) or `llm-reset-redeem --arm <vendor>/<account> --word "<his exact words>"`, which refuses (exit 2) unless those words stand verbatim in one of his own prompts of a transcript touched in the last 24 h (words.py's `human_turns`: no model text, tool result, meta, compact summary, cross-session or headless brief) and carry a reset word and the account's name in any phrasing (the model reads his intent from the intake's `reset` hint; a vendor his words name must be the one armed). Both paths are the one `arm_words`; the arm is machine-wide (`<claudeb store>/reset-arm/<vendor>-<account>`, line 1 its time, later lines `<epoch> <exit>` attempts) and `reset-redeem.log` journals who armed it and his words. `--disarm <vendor>/<account>` drops it. `--fire-armed [<vendor>/<account> [--wall weekly|unknown]]` acts only when the account is armed, its main WEEKLY window is walled and its `reset_credits` ≥ 1: the weekly verdict is the run's own when `worker_walls_kind` (`share/worker-walls.sh`) can tell — grok has one bucket, a codex reset parsed more than 5 h out, claude's `hit your weekly limit` — and otherwise the passive cache's `limits_store_wall_until` over the weekly bucket alone; when neither can tell it waits for the collector. A five-hour, Opus/Fable-only or unknown wall, no arm, or no credits (the arm stays) never fire. It then redeems once through the ordinary path (same grant choice and request id), disarms, re-reads the quota, journals `auto-fire`/`disarm` lines to `reset-redeem.log` and shows one alert line; later walls do nothing until he arms again. Exit 5 keeps the arm, at most 3 attempts 10 min apart; the third, or any exit 3/4, disarms with the reason in the alert. No usage is polled for it (robot refreshes stay off): triggers are `worker-run`'s `record_run_wall` (seconds after a run walls) and the collector right after it writes the store (the next heartbeat tick, worst case ≤ 5 min plus the collector's own run), both detached in their own session and only when an arm file exists; a flock makes the slower one skip. With `CLAUDEB_DIR` unset and any of `LLM_LIMITS_CACHE`, `LLM_LIMITS_FILE`, `CLAUDE_RESETS_ENDPOINT`, `GROK_RESETS_ENDPOINT` set it fires nothing, so a fixture can never spend a real arm. Removing the leg: `git grep -il grok` names every file that carries it — its own scripts, tests and fixtures, and the `grok`/`gr` arms elsewhere; then delete `~/.grok-profiles/` and `~/.llm-limits-grok.json`.

- `bin/opencode-go` — OpenAI-compatible client for the OpenCode **Go** subscription only
  (`https://opencode.ai/zen/go/v1`, key from keychain service `opencode-go`, never in argv;
  `run` refuses any model outside the plan's `/models` list, cached 10 minutes). The Go plan's
  own usage percentage is not exposed by any endpoint — `usage`, `limits`, `me`, `account` and
  `responses` all answer 404, so an account has exactly two knowable states. Both are recorded
  here, at the request, for every caller, as raw observations and no verdict (invariant `ai`): a
  429 naming the plan appends one `jq`-built row to `walls.jsonl`, and a COMPLETION the plan served
  stamps `<state_dir>/worker-stats/opencode-seen/<account>`. Nothing is ever deleted and nothing
  expires: a 2xx from `raw models` is not a served completion, and the two stamps are read against
  each other by `llm-limits.sh` (invariant `al`). A store write that fails is never swallowed —
  the command exits non-zero even when the answer itself arrived, or a caller would read a wall as
  retired while the record still stands. `opencode-go wall-check` re-asks a standing wall with one
  16-token completion — free, since a 429 spends nothing — and sends NOTHING unless
  `~/.llm-limits.json` says the account is walled, because a successful call would spend the
  subscription to learn what the collector already answered; its first word is the state it
  observed, `walled`, `served` or `dormant` (nothing sent), and those are not interchangeable.
  That frugal walled-only path is what `bin/llm-refresh` drives, one bare `wall-check` per walled
  profile rather than a leg-wide sweep. `wall-check --all` is the same question asked for the whole
  leg in one command, and it belongs to the menubar: its `Hard refresh` passes `--all --probe-clear`
  (either order), which drops the walled-only gate and asks every account on the roster instead,
  spending one completion on each clear one: an account's age is the stamp of the last completion
  the plan served it, so current truth for a clear account cannot be had for less. Nothing
  scheduled passes it. Latency is decided by output volume, so
  reasoning is the whole game: `--no-reasoning` negotiates `reasoning_effort:"none"` →
  `chat_template_kwargs.enable_thinking:false` → a `</think>` assistant prefix → plain, because
  which one a model accepts varies **between requests for the same model** (a rejection is a hard
  400, and the prefix can make a model answer nothing at all, which retires that strategy too).
  The gateway's own ~190s **upstream idle timeout** is the root cause of every intermittent 503
  here (opencode#30002: a reasoning model emits no output token for 2-4 minutes, the connection is
  closed for inactivity, input tokens already billed; a configurable timeout and reasoning-token
  keepalive were both declined). It is not a local bug and there is no vendor status page, so
  reproduce a failure at least twice before chasing it in this repo. Some models — grok-4.5 and the
  deepseek family — ignore every reasoning-off knob and walk straight into that timeout, but they
  do honour an explicit `--effort low`. So a stall on such a model
  is a missing budget, not weather.
  Requests are buffered and retried on 5xx; a 5xx that arrives only after `OPENCODE_GO_SLOW_SWITCH_S`
  means the generation outlived that deadline, so the next attempt streams. A transport failure —
  curl exits non-zero and reports `000` because the gateway hung, reset or spoke bad HTTP/2 —
  counts as the same class, and is the case the escalation exists for — which helps only a
  model that actually emits tokens while working, never one that is silently thinking. A
  stream's stall detector (`OPENCODE_GO_STALL_S`) is its only deadline — it deliberately carries no
  `-m` cap, because any cap short enough to matter also kills a legitimate long generation
  (`deepseek-v4-pro` needs ~1000s). `minimax-m3` ignores every strategy and needs ~38k tokens of
  thinking before it answers, so it only works with a token ceiling above that, never below it.
  **An empty answer with exit code 0 is two different bugs, and the envelope names which.**
  `finish_reason:"length"` with empty content means the whole token budget went into reasoning and
  the answer never started — suppress reasoning (`--no-reasoning`) or raise the ceiling above the
  model's thinking, and never lower `--max-tokens` to "save" anything, because the budget is spent
  on thinking first. `finish_reason:"stop"` with empty content is the opposite: the model chose to
  end the turn, which is weak instruction following, not a budget — grok-4.5 does this when a
  review methodology is injected into its prompt, and the
  `</think>` prefill strategy can trigger it in any model. Neither case is a usage limit; a real
  wall is an HTTP 429 naming `limitName`. Because both symptoms look identical from the outside,
  read `finish_reason` before changing any knob.

## The 429 taxonomy (do not conflate these)

Transient upstream 429s go to the Claude CLI, which owns retries; nothing here walls or holds on them.

1. **OAuth token-endpoint 429** — `bin/claudeb`'s `oauth_refresh()` backs off only the direct-refresh path (`oauth_backoff_until`), which runs only on a user-explicit refresh (shared-invariants row f); the warm/heal path uses its separate `oauth_heal_backoff_until` state.
2. **Warm-probe failure classification** (`bin/claudeb`'s `heal_one()`/`warm_accounts()`) — a failed zero-cost warm probe is classified into a cause (`timeout`, `warm-429`, `usage-probe-failed`, `warm-failed` = capacity-shaped upstream weather, vs. `needs-relogin`/`profile-setup` = auth-shaped), persisted as `warm_cause` in `oauth-attempts.json`. Capacity-shaped failures leave valid snapshots untouched and do not stamp auth expiry.

**Rotating a dark account** — `claudeb revive <name>` is the sanctioned replacement for the blocked curl refresh and is the one rotation a robot path may drive: `bin/claude-session-driver` runs one interactive `claudeb profile <name>` session under a PTY (no prompt, no model tokens, only `/exit` and, if that is ignored, two Ctrl-C), and the rotated token then feeds the ordinary free usage probe so `five_hour`, `seven_day` and `fable` all land in `limits/<name>.json`. Driver exits: 0 rotated, 4 the account needs a human login (revive marks `auth_needed`), 5 timeout or other failure. Revive itself also exits 4 when the usage probe answers 401/403 to a token it just rotated — a live token being rejected is the endpoint's verdict, so the flag is written rather than the account retried. Session transcripts go to `~/.claude-profiles/.claudeb/session-logs/<name>.log` in the warm-log format; rotation evidence is journaled to `token-attempts.jsonl` under kinds `session` and `revive`. An unknown account is refused without driving anything, and so is an `auth_needed` account whose token is still missing or expired; an out-of-pool account is not refused at all — that toggle is spend consent (shared-invariants q) — and `claudeb token-fresh <name>` is the read-only question about the same token this path branches on (exit 0 live, 1 expired, 2 unknown account); once the human has logged in, the live token lets revive through to the probe, whose merge clears the flag. A dark account under a robot refresh shows the stale-cause `robot curl refresh off (manual refresh only) — revive path active`; a user-explicit failure or a cause the revive path recorded (`warm_kind: "revive"` in `oauth-attempts.json`) names its observed outcome instead — the banner never masks a verdict.

## How to test

`tests/run-all $(tests/affected <file>…)` runs the suites covering those files: their own suites and those with a
catch on them (`share/suite_select.py`); a suite only naming a file runs in the full run, which is the
night's, and the runner refuses it from a worker or a chat. `share/run-suites.sh` usage covers shards,
timeouts and the slow layer; each suite's header says what it covers. No test ever calls a vendor's
real reset-redeem write.

Golden rules:
- Verify the user-visible surface (menu render, `--table` output), not just internal state.
- A Lua change goes live by itself: `config_reload.lua` (hammerspoon repo) reloads 10 s after the last save of a
  `.lua` under the config, `llm-legs/hammerspoon` or `better-terminal/hammerspoon`, once it compiles; then rerun
  `tests/e2e_surfaces.sh`.

## Reading `~/.llm-limits.json` as an LLM

Treat `stale`, `expired`, `as_of`, and `effective_pct` as the data-honesty contract. Never infer current availability from raw `used_pct` alone: keep it as provenance, check the bucket's `resets_at` against the current time, and refresh before acting on an old or rolled-over frame.

## Display contract (hammerspoon/llm-limits.lua)

- **Gray** = stale bucket (`.stale == true`), or the collector's own `.expired == true`, or the renderer's own render-time check that `resets_at` has already passed (with a clock-skew tolerance) — this last case covers a window whose reset landed between collects, before the stored `expired` flag catches up. Missing or false `.stale`/`.expired` alone is not gray; a future `resets_at` is never gray.
- **Reset time** = the collector converts raw zero, empty, absent, and 1970-era reset placeholders to `resets_at: null`; Lua renders null/absent as `–`.
- **Refresh failure** = vendor `refresh_errors` is `[{account,class,cause,at}]` from the collector (classification in `classify_cause`); `refresh_error` `{cause,at}` is derived from that list. `needs_user_entry:true` only when every entry requires a human account entry. The menu renders one dim `⚠ <account|vendor>: <class> · <age>` row per entry inside that vendor section (under the account, or under the vendor header when vendor-wide), with the raw cause in a submenu, and persists until that vendor refresh succeeds. An entry whose account is off the roster is not rendered and is dropped at the next write. Entry-only errors do not raise the global menubar `⚠`; real faults and mixed errors do. The affected account carries the same flag and renders `!` beside its data age. Top-level `refresh_error` keeps the base shape and renders as a red top row; it is reserved for no available vendor data or a full refresh with zero successful vendors. The menu also renders an observed nonzero collector exit as a red runtime error when no cache-level global error exists; any later successful task, including a passive collect, clears that runtime residue after reading a valid cache without a top-level error.
- **Red** = usage warning colors only. Claude rotation metadata is computed locally from the enabled flag and snapshot auth status.
- **Fable early warning** = when an `fb` bucket is at least 80%, only its usage-bar substring is red. The rest of the row retains its normal or stale color.
- **Table model and markers** = every row has first-class `5H%`/`WK%`/`FB%` and matching reset columns, plus `AGE`, `ROT`, `CR`, and `STATUS`; there is no `NOTE`. Rows without Fable render `-`. A `~` suffix marks a stale bucket and `!` marks an expired bucket; both may appear. `AGE` comes from that row's account/vendor `as_of`, which is the oldest timestamp among windows with a numeric `used_pct`; absent and null-valued windows do not participate (`2m`, `1h48m`, and similar).
- **Table rotation and credits** = `ROT` is `off` when the account is out of its vendor's worker pool (all four vendors) — a spend verdict only, never a refresh one: the heartbeat reads an out-of-pool account's usage like any other, `limit-5h`/`limit-weekly`/`fb:limit-fable` when a local effective percentage reaches 100, otherwise `-`. Claude `rotation.usable.general` and `.fable` remain available to worker-pick; the account projection also exposes their general hard gate as `blocked`. `CR` renders a numeric `reset_credits` as `↻N` for whichever vendor published one, including `↻0` — Codex reads it out of its usage payload, grok through `prod_mc_billing.ConsumerUiSvc/GetRemainingResets`, Claude out of the usage body's `cedar_ember` — and all three also carry `reset_credits_expires_at`, the instant the soonest still-spendable grant lapses. The menubar row shows the count and the usual data age and nothing else; the expiry rides the submenu's `Redeem usage reset · <when>` action, identically worded for every vendor.
- **Table status** = `STATUS` is `login needed` for a Codex account with `auth_needed == true`, a Claude account with a present non-`ok` `auth.status`, or a logged-out Gemini profile (`auth_needed == true`, collector-owned status `login needed`); a Grok account with `auth.status=expired` is not — the CLI refreshes it, so the row renders `-`, while `needs_login` is dead auth and is `login needed`; other unavailable rows show their collector-owned status text; all other rows render `-`. A logged-out Gemini profile records its own `refresh_error` cause from the agy helper; a successful profile refresh clears it without changing sibling snapshots.
- **Gemini account rows** = every non-removed profile gets its own account, 5h, and weekly rows; the compact single row survives only for a store without an accounts array. A logged-out profile uses the shared `Log in…`/`Hard refresh`/`Remove <name>` submenu; login opens `geminib profile <name>`, hard refresh targets `gemini/<name>`, and `main` is removed like any other name.
- **Grok account rows** = every profile gets its own account row and a WEEKLY row, and nothing else: the plan measures one pooled weekly window, so a five-hour cell must never appear and an absent one is never rendered as `?`/`nil`. Where the billing answer carried a Grok Build percentage the weekly row carries it as a `  build N%` detail suffix beside the pooled number — the pooled window is what is spent, the Build share is only which product spent it. A profile with no usable login renders the shared `login needed` row with the `Log in…`/`Hard refresh`/`Remove <name>` submenu, like a logged-out Gemini profile.
- **Plain model** = each line mirrors the table's labeled 5h/weekly/Fable values and resets, age, rotation, credits, and status. The same `~`/`!` markers apply, and a standing run-observed wall (shared-invariants bz) reads `walled→<reset>` as the status.
- **In-flight indicator** = one `⟳ ` for every menu: each module reports its running refreshes through `menu-style.lua` `busySource` (LLM limits, Doctors, Token tracking), and `tests/test_menu_refresh_marker.sh` fails on a task nobody classified. Passive menu-open collects never render an indicator. Verified-live explicit, hard, and start-window tasks share one registry and prefix the normal menubar title with `⟳ ` immediately; standing vendor or global errors prefix it with `⚠ ` when no explicit task is active. Resume-timer text remains visible. Ordinary and start-window entries each have a cleanup budget, but an over-budget task that still reports running remains registered and suppresses duplicates; only a verifiably-dead entry is removed.
- **Checkbox ("In pool")** appears on every logged-in real account row of all four vendors (`enabled` = neither explicitly excluded nor shielded; the separate `shielded` boolean says which of the two it is) — toggling it calls that vendor's own `enable`/`disable`. What the list itself shows for an in-pool account depends on the vendor's role switches: with both roles on it is the system checkmark, while either role is off the account name is dimmed, and with both roles off the row and the submenu item show no check at all — a check under a fully closed vendor would read as an account the routers spend. The mark is derived at render time, never stored, so switching a role back on restores it; clicking "In pool" while any role is off switches the off roles back on and leaves membership as it stands. An out-of-pool row shows nothing either way. It consents to SPEND and nothing else: an excluded account is still refreshed by the heartbeat and `claudeb revive` still takes it. The compact sole-account Gemini row carries it too — no membership is immutable. A **login-needed** row deliberately has none: pool membership on it would claim an availability the account does not have; the stored exclusion survives and reappears once it is logged back in. An explicit/pinned Claude profile entry is not part of `claudeb-store` and so still has no checkbox.
- **"Pin for workers"** on each logged-in account row toggles that one account in the vendor's pin list via `<vendor>b use` / `use --unpin <name>`; a login-needed row offers it only when that account is currently pinned, so a stale pin can always be removed. Every pinned account shows `●`, uncoloured even where the router will not honour it. A pin absent from the rendered account rows gets a gray clear-only row, so removed profiles and stale configuration remain visible. Pool exclusion alone does not hide a pin.

## Claude Code statusline hooks

`statusline-workdir-hook.sh` appends this chat's place journal through `bin/statusline-place add`;
its registrations and rules are `docs/statusline-contract.md` "Shown tree".
`statusline-place why --session <session_id>` is the diagnostic: the shown tree, the line that
chose it, any fallback, and the last 10 lines.

State files are stored at:
- `~/.cache/claude-statusline/place-<session_id>`
- `~/.cache/claude-worker-tags/<session_id>/<agent_id>`

`worker-tag-hook.sh` prefixes a fork's `fork · <model> · <account>` tag, seeded by
`worker-spawn-hook.sh`, onto the fork's later Bash activity descriptions. It exits
silently for any `hook_event_name` other than PreToolUse (its rewrite payload hardcodes
`hookEventName: "PreToolUse"`, so a mis-registration must be a no-op).

`limits-triage-nudge.sh` (PostToolUse matcher `Bash`) scans Bash tool output for a limit-shaped
pattern (`no available accounts`, `API Error: 503/529`, `usage limit`, `overloaded`,
`anthropic-ratelimit`, `CLAUDEB_USAGE_LIMIT`, `claudeb ... timed out`) alongside a
claude/claudeb/anthropic/fable context word in the same output, and nudges the session to run
`llm-limits --table --no-write` instead of theorizing. Dedup: one nudge per session per
15 minutes, state in `/tmp/claude-limits-triage-nudge-<session_id>`.

To disable any of these hooks, remove its entry from `hooks.PostToolUse` or `hooks.PreToolUse` in
`~/.claude/settings.json`.

Debug place tracking:
`jq -cn --arg dir "$PWD" '{hook_event_name:"PostToolUse",tool_name:"Bash",session_id:"debug",cwd:$dir,tool_input:{command:("cd " + ($dir | @sh))}}' | ~/.claude/hooks/statusline-workdir-hook.sh; statusline-place why --session debug`
