# Diagnostics: llm-legs multi-account/limits ecosystem

For LLM sessions asked to fix limits, the menu, or claudeb. Read this before touching code.

## System map

- `llm-limits.sh` — read-only collector, writes `~/.llm-limits.json` (schema `{schema, fetched_at, vendors}`). A failed vendor refresh preserves its last valid buckets and records `vendors.<vendor>.refresh_error` as `{cause,at}` with optional `needs_user_entry:true`; passive collects preserve that outcome, and the next successful refresh of that vendor clears it. A full refresh with no successful vendor records the same base shape at top-level `refresh_error` and exits nonzero; partial and targeted failures exit zero. `--refresh` polls free usage endpoints; `--start-windows` is the only paid path (never call from scripts). `--table`/`--plain`/`--json` control rendering; piped output defaults to JSON.
- `bin/llm-refresh` — the escalating refresh driver behind the `com.llm-refresh` launchd heartbeat (`~/.local/libexec/llm-refresh-heartbeat` wrapper, 300s StartInterval; `bin/llm-refresh install-agent`/`uninstall-agent`). Per-vendor cadence state in `~/.llm-limits-refresh.state`, one JSONL line per vendor per due tick in `~/.llm-limits-refresh.jsonl` (`outcome` ∈ `fresh-passive|refreshed|partial|pushback|error`, plus OpenCode's own three below: `dormant|walled|reopened`; `partial` names the accounts still stale, and accounts no refresh can help — removed or auth-dead; worker-pool membership is spend consent and never gates a refresh — are never targeted and are listed as `unrefreshable:` in the detail instead of pinning the vendor at `partial`). Every vendor starts at 30 min on one ladder (15→22→30→45→60): a 429/rate-limit signal — from collector stderr or the store's `refresh_error` fields — loosens one rung, 72h with none tightens one rung, so per-vendor cadences diverge only from observed pushback, never by assumption. Step 0 is one passive collect shared across due vendors; step 1 runs `--refresh-account <vendor>/<account>` per still-stale account — except Claude, whose token endpoint is vendor-blocked: its step 1 splits the stale accounts by what `claudeb token-fresh <account>` says. A token that still carries a request needs no session — `claudeb revive` on it is one usage-endpoint GET — so EVERY such account is revived in the same tick, under the tick lock, `timeout`-guarded at `LLM_LIMITS_REFRESH_PROBE_TIMEOUT` (default 90s) and with no attempt stamp, since a live chat rotates its own token and must never wait for a session slot. Only an expired token needs `claudeb revive <account>` as a real session, and that is still one per tick (the least recently attempted of the expired accounts — every session attempt, success or failure, stamps `vendors.claude.attempts.<account>` in the state file, so a persistently failing account rotates out of the way instead of owning every tick; ties go to the stalest — `timeout`-guarded at `LLM_LIMITS_REFRESH_REVIVE_TIMEOUT`, default 240s; the rest wait for the next tick, and the detail says so, naming what it `probed:` and what it opened a `session:` for; Claude's reserved `main`/`-` names are `unrefreshable` too, since no revive can take them), followed by a collect so the rotated snapshot reaches the merged store. That interactive session holds no tick lock: the attempt stamp is persisted to the state file BEFORE the lock is handed back — otherwise a tick starting meanwhile picks the same account and opens a second session on it — the state is re-read from the file after the lock is reacquired, since whoever held it in between owns what is on disk, and a tick that cannot get the lock back stops there instead of racing the new holder through the remaining vendors. A revive that needs a human login — a login screen, or a usage 401/403 against a token it just rotated — makes that account `unrefreshable` and journals `error` — never `pushback`, which is reserved for a real 429 from the session. Tick lock `<state>.lock`, broken by holder liveness: a dead holder at once, a live one never until a 3600s ceiling, an ownerless directory after 1800s. OpenCode is the inverted fourth vendor: the Go plan publishes no usage endpoint, so there is nothing to collect passively and its only probe is a real completion. With no walled account in `~/.llm-limits.json` it is dormant — outcome `dormant`, zero requests, no passive collect started on its account — because every real call already records its own outcome (invariant `ai`). A standing wall is probed one `opencode-go wall-check` per walled account, which is free while the window is shut, and the tick lock is handed back while it is out so a wedged gateway holds no other vendor's tick. The probe answers in three states and the journal keeps them apart: outcome `walled` when the gateway repeats the 429, `reopened` when the plan SERVES the completion (the only thing that ends a wall, recorded as that account's served stamp — no record is ever dropped), and `dormant` when the wall went between the read and the request, so nothing was sent; the first two re-collect, so the rows every surface reads follow the probe. Whether a wall stands it asks the collector and never the record (invariant `al`). Its rung is read off the stated reset — day-granular, so approximate: within an hour of it, past it, or with none stated the ladder tightens and keeps probing, since only a served request ends a wall.
- `share/store-lock.sh` — mkdir-based lock serializing every read-merge-write of `~/.llm-limits.json`: `llm-limits.sh` re-reads previous state INSIDE the lock right before the jq merge, network stays outside, the write is an atomic `mv`, pid-owned with a rename-aside break by holder liveness — a dead holder at once, a live one never until a 3600s ceiling, an ownerless directory after 30s (env-overridable; only the owner may release), skipped entirely under `--no-write`. Concurrent collector invocations (heartbeat tick racing a menu refresh) can no longer drop each other's vendors.
- `bin/claudeb` — account prober/launcher. Snapshots per account in `~/.claude-profiles/.claudeb/limits/<name>.json`:
  ```json
  {"five_hour":{"used_percentage":6,"resets_at":1784044800,"as_of":1784031056,"origin":"usage"},
   "seven_day":{...}, "fable":{...}, "auth":{"status":"ok","checked_at":1784031056}}
  ```
  `origin` ∈ `usage|headers|cached`. `auth.status` is only ever `"ok"` or `"expired"` (never `needs re-login`/`auth_needed` — those are free-text `cause`s or Codex-only concepts, respectively).
  **Account existence is one set** (shared-invariants row x): `account_names` unions `tokens/`, `limits/*.json`, and the `~/.claude-profiles/<name>` dirs (reserved `main`/`-` filtered), and every verb — `status`, `enable`/`disable`, `warm`, probes, `use` pin validation — consults it, so a keychain-only browser login (no setup token) is as real as an `add`ed account. Account birth (`add`, first-launch profile create) fires a detached targeted collector refresh and removal fires a passive collect (`share/account-announce.sh`), so the menu follows without a manual refresh.
  **Display semantics are one view** (shared-invariants row y): `share/limits-view.sh` is the single definition of stale/expired/effective and of cell text (`limits_pct_text` = effective value + `~` stale / `!` expired markers, bare `-` when unmeasured; one reset formatter, one age formatter, age = oldest measured bucket). `bin/claudeb` and `llm-limits.sh` prepend `$LIMITS_VIEW_JQ`; the menu renders the collector's precomputed `effective_pct`/`stale`/`expired` fields. So "menu shows fresh, claudeb shows stale" is by construction impossible for pct cells — `tests/e2e_surfaces.sh` proves it live against the real store. Any probe/warm that rewrites snapshots announces one passive collect (`announce_limits_probed`; the collector suppresses its own children via `LLM_LIMITS_ANNOUNCE_SUPPRESS`), and a pressed `r` in the status TUI carries `CLAUDEB_WARM_USER_EXPLICIT=true` so the token-freeze experiment cannot silently eat it.
  Two independent OAuth-heal paths sharing `oauth-attempts.json`: **warm** (drives the real `claude` CLI's own OAuth rotation, zero-cost, comment at `bin/claudeb:632-635` — a token-endpoint 429/failed record must never gate it) and **direct refresh** (claudeb's own curl POST to the token endpoint, `oauth_refresh()`). `.claudeb-state` = current account name (single line); `disabled` = one excluded-account name per line, absent file = all enabled — this is the **worker pool**, and all three vendors now share it (`share/worker-pool.sh`, one file per vendor: `~/.claude-profiles/.claudeb/disabled`, `~/.codex-profiles/.codexb/disabled`, `~/.gemini-profiles/.geminib/disabled`; the dot-directory keeps it outside the profile enumerators' `*` glob). Exclusion is a WALL for every headless run: `worker-pick` and `codexb pick` skip the account, and `claudeb … -p`, `codexb <name> exec`, `geminib profile … --print` and `worker-run start --account <name>` refuse it outright — only the vendor pin in `~/.claude/worker-model` overrides. An interactive session is the user and is never gated, so any member may go out, the last one included; an empty pool then answers `every <vendor> account is out of the worker pool` and `worker-run` reports `OUTCOME: <VENDOR>_UNAVAILABLE`, never a usage limit. `claudeb enable|disable`, `codexb enable|disable`, `geminib enable|disable`; the state is visible in each tool's own `list`/`status` (`(out of pool)`), in the table's `ROT` column (`off`), and as the menu checkbox.
  Entry points, and the whole reason there is no daemon: an **interactive** run must name a profile (`claudeb profile <name>`; bare `claudeb` and any argument list without `-p`/`--print` print the profile list and exit 2), while a **headless** run (`-p`/`--print`, i.e. a program calling claudeb — find-truth, usage-ai-report, any script) takes its account from `worker-pick --account claudeb` and then runs exactly the `claudeb profile <acct> …` path — in-process, so there is no second `claudeb` in the process tree. That path has no wall, no hold, and no retry: nothing selectable exits immediately with the query's own **3** (a caller choosing between "retry after the reset" and "this is misconfigured" needs those apart), a missing or unusable `worker-pick` exits 2, and no request is ever parked until it becomes a 503. `CLAUDEB_WORKER_PICK` overrides the binary (a sibling of the resolved script wins over `PATH`, so both halves of the query contract come from one checkout). Headless runs never restamp `.claudeb-state`. `claudeb use <name>` writes the same `claudeb_profile=` pin in `~/.claude/worker-model` that `/worker claudeb <name>` sets — the pin every consumer already reads (worker-pick routing, `worker-limit-gate.sh`, the statusline `w:cb @`) — leaving `worker=` alone so naming an account cannot also re-route work to another vendor; `use` with no name prints the pin, `use --clear` removes it, an unroutable name is refused, and an out-of-pool account is accepted with a note that the direct pin overrides automatic pool exclusion.
- `bin/codexb` + `codex-quota.py` — same idea for Codex CLI, no proxy: per-account `CODEX_HOME` under `~/.codex-profiles/<name>`; quota via zero-spend app-server RPC (`account/rateLimits/read`), cached in `~/.llm-limits-codex.json`. `codexb status` prints one line per account (`main: Logged in ... | 5H ... | WEEKLY ...`); an account needing login shows `auth_needed`/`Not logged in` with no usage buckets.
- `bin/geminib` + `agy-quota.py` — Antigravity profiles without touching the live login: `main` uses the real `HOME` and is removed like any profile — `geminib remove main` leaves only the marker `~/.llm-limits-gemini.json.removed`, the same file the menubar's `llm-limits.sh --gemini-remove` writes (delete it to bring `main` back; nothing else ever clears it); named profiles run with `HOME=~/.gemini-profiles/<name>`. There is no supported narrower profile flag or environment variable. Shared Gemini settings and Playwright driver/browser caches are symlinked from the base HOME while authentication remains isolated. `geminib profile <name>` creates and launches a profile for its one-time Google login; `list`/`status` probe each profile independently. Main quota stays in `~/.llm-limits-gemini.json`; named caches live in `~/.llm-limits-gemini/<name>.json`.
- Every side's first account is special by history, not by design: codex `main` runs with `CODEX_HOME` removed, the OpenCode profile literally named `-` means "no profile" and synthesises the account name `opencode-go`; gemini `main` (the real `HOME`) was removed on 2026-08-25 through its marker. Take it on when he asks, never as a side effect of other work.
- `bin/review-bench` — blind review benchmark runner. The binary is a shim: it puts `share/` on `sys.path` and calls `rbench.cli.main`, so the program itself is the package `share/rbench/` — fourteen modules in dependency order (`store`, `catalog`, `raters`, `accounts`, `scope`, `panel`, `prompts`, `launch`, `verify`, `round`, `debt`, `report`, `stats`, `cli`) whose `__init__` re-exports every public name but store's `REPO_ROOT`/`BIN_DIR` path anchors, which its siblings read off `store` itself. Each name is owned by exactly one module, recorded in `share/rbench/name-to-module.json`, which is what the suites' `rb.<module>.<name>` patch targets are checked against; inside the package a module reads its siblings through the module object, never through a `from .x import y` binding a test could no longer patch. `REVIEW_TIERS` is the canonical T0–T3 policy: every cell is parsed when the module loads, `review-bench tiers` prints the budgets, uses and cells, and `review-bench review <commitish> --tier Tn` resolves the tier into the existing explicit-rater run path. A `review` DETACHES its panel (`start_new_session`, output to `<run-dir>/panel.log`, pid in `panel.pid`), prints the run id as soon as the run has a `meta.json` and returns, so the harness's ten-minute kill can no longer take a tier down with it; `review-bench wait <run-id>` blocks on that pid and then prints exactly what a foreground run printed after its panel, teed by the run itself into `<run-dir>/panel.handoff` with its exit code in `panel.exit`, and on a panel that died prints the tail of `panel.log` instead and points at `doctor`. `--foreground` keeps everything in one process and is how the suites drive a panel. `--worktree` (on `review` and `run`) reviews the uncommitted working tree: the dirty tree is wrapped in a synthetic unreferenced commit (fixed identity and date, so an unchanged tree re-snapshots to the same sha) that the whole pipeline consumes like any commit; such runs mark `worktree: true` in meta, are refused by `record` (snapshot commits are GC-prunable, so a corpus row keyed on them would dangle), and pin errored-cell reruns to the snapshot sha. `--range A..B` (on `review` and `run` alike) reviews a span of commits as ONE change — a branch, a series of fixes, work already pushed: the right end's tree is sealed over the left end as its parent, so the range is a single diff every reader downstream already knows how to consume, and the same spelling-independent seal makes it deterministic. A rerun is pinned to that seal and carries no flags at all, so it reads the range's own ends back out of the seal — announcing and pricing itself as the same range rather than as the tool's own commit. Such a run stays out of the corpus like any sealed snapshot, but unlike a worktree run it stamps the repository's receipt only when its right end IS the current tree — a review of old history that moved that receipt would answer for code it never read. Chunking is off by default: `--chunk` asks for it, and a commit whose whole diff runs past `DIFF_CHUNK_THRESHOLD_BYTES` (800000) gets it whether anybody asked or not, that being the only size at which a diff-fed cell dies deterministically (argv past ARG_MAX, the vendor's own input ceiling, a context length — invariant row `ax`). Either way the diff is split at FILE boundaries into chunks packed toward `DIFF_CHUNK_TARGET_LINES` (800) — the target bounds a chunk holding more than one file; a single file whose own diff is bigger is one oversized chunk read whole, and a commit that IS such a file is handed out unsplit. Chunking splits the DIFF and never the panel: each cell keeps its one spec and reads its chunks one after another (`run_rater_chunks`), so the panel holds exactly the cells its tier asked for — still ONE run, one receipt, one handoff, with the chunk count on the target line and the reason on the line the run prints beside it. Every run prints the target it resolved before the panel starts (`base..head`, files, lines, scope, one line per repository) and refuses an empty one outright: the target was implied by the flags and printed nowhere, so a run pointed at the wrong one came back confirming nothing, which reads exactly like a clean review of the right one. `--repo` is repeatable alongside `--worktree`, which is how a change spanning a producer and its consumer in two checkouts is reviewed by ONE panel instead of two blind ones: each repository is sealed exactly as a solo `--worktree` run seals it, and their snapshots are mounted under one directory prefix each (the basename, numbered on collision) into a synthetic workspace under `<state_dir>/merged/<merged-sha>` whose own snapshot commit is the whole cross-repository diff — so the raters, the sealed clones, the verifier's file lookups and the finding-path resolution all keep working against a single repository, and a finding's path names the repository it is about. The workspace borrows the members' objects to build and repacks them into itself, refusing to run while anything is still borrowed (a gc in a member would take the reviewed code with it), is named after the commit it holds (so a rerun, which is pinned to that commit and carries `--repo <workspace>`, finds it already on disk), carries a `.review-bench-merged.json` manifest naming the repositories it was built from, and is pruned once the run can no longer be rerun (`TRIAGE_GATE_HOURS`). `--paths` entries then start with the repository's own prefix (`producer/rates.json`) or are absolute, and a repository none of them names keeps its whole working tree. The run writes each member's OWN receipt against that member's snapshot — the one non-negotiable, since a merged review that stamps one repository and forgets the other leaves `review-bench receipt` in the forgotten one naming no run for a review that read it — records the members in `meta.repos`, names them in the adjudication handoff, stamps a `repo` field into every finding, writes one live-progress document per member so the review is visible in each repository's statusline, and is owed its report in any of them. Each `--repo` may also name a range of its own as `--repo <path>@<base>..<head>`, which is how the ordinary shape of a cross-repository change — one half already committed on a branch, the other still in the working tree — reaches ONE panel: a member named with a range is sealed as `--range` seals a solo run, is announced by its own ends, and stamps its repository only where that range's right end IS the tree standing in front of the reader, while a member named bare is read from its working tree as before. One repository named that way and nothing else is simply that repository's `--range` run, workspace and all skipped. `--paths` narrows a ranged member too — the parent becomes a synthetic left end holding the range's own base content at those paths and the right end's everywhere else, so the sealed diff is the range restricted to them while the tree the raters browse stays whole, and a pathspec outside the range's diff is refused by name — while the target flags the inline range duplicates are refused as before (`--range`, a commitish, `--worktree` where every member carries a range) and a bare repository beside a ranged one with no `--worktree` to say how it is read. Multiple `--repo` without `--worktree` or a range apiece, a repository named twice, a member with a clean tree and the workspace itself as a tree to seal are all refused before anything is sealed. Every run also maintains an atomic live-progress file `progress/<receipt-name>-<pid>.json` (tier, target, cells, done, failed) for the statusline reader, pruning entries whose pid is dead and unlinking its own on the way out — liveness is the reader's to derive from pid+mtime. `review-bench review --debt --tier Tn` is the self-scoping review the commit gate prints — scope and synthetic base per `docs/review-contract.md` §Debt; it takes no target and no `--paths`, and `--repo` is repeatable here too, one debt scope per member. `review-bench debt --repo <top> [--session <sid>] [--paths <p>…] [--list]` answers the gate's one machine question in one line, always exit 0: `none`, `debt <n> mine|other|unknown [<owned>] [(+<f> foreign)]` — with the ownership word dropped entirely (`debt 2`) where no session was named and every debt path is on some chat's record, and no foreign share on a session-less line at all, since nothing is asking and nothing is skipped; the count is never `0`, an empty debt having answered `none` already — or `timed-out <run-id>`, with `--list` printing the debt paths; verdict semantics and the `waive` refusal live in `docs/review-contract.md`. `--list` and `--split` name the ledger they read on stderr (`ledger: <common git dir>/claude-review-debt` — one ledger per git family, shared by every worktree; a linked worktree's leftover ledger is folded into it on first read). `review --reason` without `--this-repo-only` is a warning kept on the run's meta, never a refused launch. Nothing here proposes a tier: the chat picks one. T3 and any tier's `--max` are still the owner's to start, in code rather than in prose — `guard_tier_owner` refuses both unless a fresh marker names the panel or the caller is Egor's own shell — a terminal on both ends with no `CLAUDECODE` in the environment, so a pseudo-terminal an agent opens for itself is not mistaken for him. Hand-assembled `--raters` are deliberately ungated: that is the bench, not the everyday review the ladder prices. Antigravity cells are explicit-only and always run the review skill (`--raters agy-pro-<low|high>-skill`, `agy-flash37-<low|medium|high>-skill`, `agy-flash36-<low|medium|high>-skill`, or `agy-flash35-<low|medium|high>-skill`; a skill-less spelling is refused) and launch through `geminib profile <account>`, since agy resolves its Google account from HOME and takes no account flag. Every run executes in a sealed clone and keeps `raw-<rater>.md`, `agy-<rater>.log`, `usage-<rater>.jsonl`, and normalized `findings-<rater>.jsonl` under the run directory. Empty, malformed, error, and headless permission-denied output fail closed. Skill cells invoke the imported official Gemini CLI `code-review` extension; its Markdown is adapted to the shared finding schema. OpenCode cells (`oc-*`, optionally suffixed `-anthropic`/`-google` to inject a published review methodology into the toolless prompt) share one subscription gateway: the gate admits the longest expected job first (and cells are submitted slowest-first, since priority only orders what is already queued), because the gateway parallelises fine and the makespan is decided by whether a slow cell waits behind fast ones. Each cell's deadline and token ceiling are scaled from its measured cost rather than shared, and a cell that summarises the diff instead of reviewing it — one low-severity change description per hunk, which parses as findings and looks productive — fails closed. A model that ignores reasoning suppression is offered only with an effort (`OPENCODE_EFFORT_REQUIRED_MODELS`), because the effortless spec would stall the gateway for minutes; every model that rule has ever named is retired today. `--verify <oc-model>` checks every finding back against the file it cites with a second cheap in-plan call and keeps only the survivors, writing the full judgment to `verified-<rater>.jsonl`; it fails open on an unusable answer. It is a TIER REVIEW's stage and nothing else (2026-08-14): a tier defaults it on, while a bench run refuses `--verify` by name, takes the `--no-verify` older reproduce lines spell as a no-op, and records what the raters said — a row the verifier already filtered measures the pair rather than the cell. The verifier is resolved through the same `parse_rater` refusals as a cell (a model measured unusable, or one that needs an explicit effort, cannot verify) and obeys the same 429 stop-the-run rule — findings left unchecked by a wall are counted in `verifier_unverified`, so an unverified run never reads as a verified one. A throttled verifier is retried on the next model of `OPENCODE_VERIFIER_CHAIN`, so the model that answered is recorded per finding and tallied per cell in `verifier_by_model`, and the report's `verifier:` line names who judged, how many were checked and how many were kept unchecked — a panel holding OpenCode cells always carries the line, reading `off` when no verifier ran, because a silent line and a verified run are indistinguishable to the reader. Every side must declare a clean review with the literal marker `NO FINDINGS`: an empty findings file otherwise means the rater answered in prose or stopped mid-turn, and that cell is recorded as errored to be rerun rather than as a commit with nothing wrong with it. Finding paths are canonicalised to repository-relative form first, since raters cite markdown links, absolute paths and sealed-clone paths that otherwise defeat both the file lookup and deduplication. `review-bench oc-models` prints what the tool actually knows about the gateway: the measured capability table (`OPENCODE_MODEL_FACTS` — whether reasoning-off works, whether an effort scales thinking, measured review seconds) next to the recorded per-cell success rate from every past run, so a model that starts failing is visible without editing prose. A cell measured unusable is refused by name with its evidence. Account handling is shared by every side: `SIDE_RUNNERS`/`SIDE_WALL`/`SIDE_POOL_VENDOR` in `share/rbench/{launch,accounts}.py` say how a vendor launches, how it words an exhausted account, and which pool vendor it is, and one runner then asks `worker-pick --account <vendor> [--exclude …]` for each attempt, retires a walled account for the rest of the run (keyed per quota bucket, since Claude bills fable separately and Gemini bills per model, so a walled 3.1 Pro must leave that account's flash cells alone), and records the account that actually answered — so an OpenCode 429 (its own dollar window, not weather) stops that side outright while Gemini or Claude simply continue on the next account. Before the panel starts, every side the pool staffs — Claude, Codex and Gemini alike — is asked of `worker-pick` and skipped by name when it cannot be staffed, so a walled account costs one skip line instead of a report full of errored cells and a rerun line offering them again. A spent gateway plan is recorded the same way — `SIDE_WALL` recognises the wording and `mark_walled` stores its reset — but a gateway that is merely DOWN says nothing about when it is back, and that case gets a wait of the tool's own: a cell family whose every attempt in a run failed ON THE GATEWAY (`gateway_outage` — not a plan wall, not the pool behind it running dry, not a review that came back as prose) is written into `<state_dir>/gateway-cooldown.json` with the moment it may be tried again (45 minutes, held under a lock like every other state file), and the following runs inside that span launch exactly ONE attempt of it — the canary, whose answer clears the wait and whose failure extends it from the moment the outage began. The wait expires by the clock rather than by proof of recovery, because a cell held out until it proves it recovered is never asked for that proof; nothing sweeps the file. A wall must never reach this path: its reset is hours or days away, and a canary fired into it every 45 minutes is precisely the retry this table forbids.

  A review-bench rater reviews commit X in isolation from every descendant of X, because descendants usually contain the fixes. Every current and future rater path must use a sealed view, either a sealed clone or a SHA-pinned prompt, and every new rater kind must be added to the guard test.
- `bin/review-owner-gate.sh` — the session half of that gate, registered twice in `~/.claude/settings.json`. `prompt` (UserPromptSubmit) touches `<state_dir>/review-grants/t3` or `.../max` when Egor's own message names one («T3», «макс ревью», «полное ревью», “max review”, the flags); `bash` (PreToolUse) denies a `review-bench review|run` whose own launch segment carries `--tier T3` or `--max` while no marker under half an hour old sits there. The `bash` mode anchors on the tool starting a command, so a `grep` quoting one is neither a launch nor a denial. - `bin/worker-pin-gate.sh` — the same shape for the account pin, which is Egor's own override above the pool and not a routing convenience a session may reach for. Registered three times in `~/.claude/settings.json`: `prompt` (UserPromptSubmit) touches `<state_dir>/pin-grants/pin` when his own message names the pin — in either direction, since a pin he set is not a session's to clear either — while `write` and `bash` (PreToolUse) deny a session moving the pin inside `~/.claude/worker-model` by hand, through Edit/Write and through a shell redirect alike, whenever no marker under half an hour old sits there. What is denied is the PIN, not the file: `/worker` rewrites `worker=`, `*_model=` and `*_effort=` in that same file, so a write leaving every `*_profile=` line as it found it passes ungated, and every door compares the resolved file rather than the path text (`//`, `..` and `~` all name the one pin). The command path is refused elsewhere, inside `worker_model_pin_account` (`share/worker-model.sh`), because that is the one chokepoint every spelling of `claudeb|codexb|geminib use` reaches; that half applies only to a session (`CLAUDECODE` in the environment) writing the real file, so the menubar — a Hammerspoon subprocess carrying neither — and every test fixture named through `WORKER_PICK_CONFIG_FILE` are untouched. - `bin/opencode-go` — OpenAI-compatible client for the OpenCode **Go** subscription only
  (`https://opencode.ai/zen/go/v1`, key from keychain service `opencode-go`, never in argv;
  `run` refuses any model outside the plan's `/models` list, cached 10 minutes). The Go plan's
  own usage percentage is not exposed by any endpoint — `usage`, `limits`, `me`, `account` and

  here, at the request, for every caller, as raw observations and no verdict (invariant `ai`): a

  stamps `<state_dir>/worker-stats/opencode-seen/<account>`. Nothing is ever deleted and nothing

  each other by `llm-limits.sh` (invariant `al`). A store write that fails is never swallowed —
  the command exits non-zero even when the answer itself arrived, or a caller would read a wall as
  retired while the record still stands. `opencode-go wall-check` re-asks a standing wall with one
  16-token completion — free, since a 429 spends nothing — and sends NOTHING unless
  `~/.llm-limits.json` says the account is walled, because a successful call would spend the
  subscription to learn what the collector already answered; its first word is the state it
  observed, `walled`, `served` or `dormant` (nothing sent), and those are not interchangeable.
  That frugal walled-only path is what `bin/llm-refresh` drives, one bare `wall-check` per walled
  profile rather than a leg-wide sweep. `wall-check --all` is the same question asked for the whole
  leg in one command, and it belongs to the menubar: its `Hard refresh` passes `--all --probe-clear`
  (either order), which drops the walled-only gate and asks every account on the roster instead,
  spending one completion on each clear one: an account's age is the stamp of the last completion
  the plan served it, so current truth for a clear account cannot be had for less. Nothing
  scheduled passes it. Latency is decided by output volume, so
  reasoning is the whole game: `--no-reasoning` negotiates `reasoning_effort:"none"` →
  `chat_template_kwargs.enable_thinking:false` → a `</think>` assistant prefix → plain, because
  which one a model accepts varies **between requests for the same model** (a rejection is a hard
  400, and the prefix can make a model answer nothing at all, which retires that strategy too).
  The gateway's own ~190s **upstream idle timeout** is the root cause of every intermittent 503
  here (opencode#30002: a reasoning model emits no output token for 2-4 minutes, the connection is
  closed for inactivity, input tokens already billed; a configurable timeout and reasoning-token
  keepalive were both declined). It is not a local bug and there is no vendor status page, so
  reproduce a failure at least twice before chasing it in this repo. Some models — grok-4.5 and the
  deepseek family — ignore every reasoning-off knob and walk straight into that timeout, but they
  do honour an explicit `--effort low`: grok-4.5 reviewed a 54k-token diff in 8-91s over six runs
  with no failure, against 196-436s with 503s on the reasoning-off path. So a stall on such a model
  is a missing budget, not weather.
  Requests are buffered and retried on 5xx; a 5xx that arrives only after `OPENCODE_GO_SLOW_SWITCH_S`
  means the generation outlived that deadline, so the next attempt streams. A transport failure —
  curl exits non-zero and reports `000` because the gateway hung, reset or spoke bad HTTP/2 —
  counts as the same class, and is the case the escalation exists for — which helps only a
  model that actually emits tokens while working, never one that is silently thinking. A
  stream's stall detector (`OPENCODE_GO_STALL_S`) is its only deadline — it deliberately carries no
  `-m` cap, because any cap short enough to matter also kills a legitimate long generation
  (`deepseek-v4-pro` needs ~1000s). `minimax-m3` ignores every strategy and needs ~38k tokens of
  thinking before it answers, so it only works with a token ceiling above that, never below it.
  **An empty answer with exit code 0 is two different bugs, and the envelope names which.**
  `finish_reason:"length"` with empty content means the whole token budget went into reasoning and
  the answer never started — suppress reasoning (`--no-reasoning`) or raise the ceiling above the
  model's thinking, and never lower `--max-tokens` to "save" anything, because the budget is spent
  on thinking first. `finish_reason:"stop"` with empty content is the opposite: the model chose to
  end the turn, which is weak instruction following, not a budget — grok-4.5 does this when a
  review methodology is injected into its prompt (2 of 3 passes, after 88-122s), and the
  `</think>` prefill strategy can trigger it in any model. Neither case is a usage limit; a real
  wall is an HTTP 429 naming `limitName`. Because both symptoms look identical from the outside,
  read `finish_reason` before changing any knob.

## The 429 taxonomy (do not conflate these)

Transient upstream 429s are still real. They are passed to the Claude CLI, which owns its
retry behavior; this project no longer turns them into account walls, holds, or locally
generated 503 responses.

1. **OAuth token-endpoint 429** — `bin/claudeb`'s `oauth_refresh()` backs off only the direct-refresh path (`oauth_backoff_until`); the warm/heal path uses its separate `oauth_heal_backoff_until` state.
2. **Warm-probe failure classification** (`bin/claudeb`'s `heal_one()`/`warm_accounts()`) — a failed zero-cost warm probe is classified into a cause (`timeout`, `warm-429`, `usage-probe-failed`, `warm-failed` = capacity-shaped upstream weather, vs. `needs-relogin`/`profile-setup` = auth-shaped), persisted as `warm_cause` in `oauth-attempts.json`. Capacity-shaped failures leave valid snapshots untouched and do not stamp auth expiry.

**Token-freeze switch** (experiment, see `docs/EXIT-PLAN.md`) — the file `~/.claude-profiles/.claudeb/token-freeze` (JSON `{started_at,until,reason}`; `until` in the past or missing = ignored/held) freezes every ROBOT path to the OAuth token endpoint: `oauth_refresh()`'s curl POST, `token-upkeep`, and warm sessions without the menu's explicit user signal all short-circuit. Phase 2 exempts the full invocation launched by every user menu refresh (global `Refresh`, global `Refresh + Start Windows`, and per-account Hard refresh), including its warm, heal, and direct curl-refresh steps; scheduled/background paths stay frozen. Every token-endpoint-relevant event — real attempts and outcomes, warm outcomes, adoptions, and freeze skips — is journaled append-only to `~/.claude-profiles/.claudeb/token-attempts.jsonl` (`{ts,account,kind,outcome,http,pid}`), with `"user":true` added only for events in a user-explicit invocation; a `frozen-skip` outcome means the freeze held that path (deliberate evidence, not an error). A dark account under a robot refresh renders its stale-cause as `curl refresh frozen (experiment) — revive path active`; a user-explicit failure, and any cause recorded by the revive path itself (`warm_kind: "revive"` in `oauth-attempts.json`), instead name the observed token-refresh, warm, usage-probe, or timeout outcome — the freeze never masks the escalating refresh's own verdict.

**Rotating a frozen account** — `claudeb revive <name>` is the sanctioned replacement for the blocked curl refresh and is exempt from the freeze: `bin/claude-session-driver` runs one interactive `claudeb profile <name>` session under a PTY (no prompt, no model tokens, only `/exit` and, if that is ignored, two Ctrl-C), and the rotated token then feeds the ordinary free usage probe so `five_hour`, `seven_day` and `fable` all land in `limits/<name>.json`. Driver exits: 0 rotated, 4 the account needs a human login (revive marks `auth_needed`), 5 timeout or other failure. Revive itself also exits 4 when the usage probe answers 401/403 to a token it just rotated — a live token being rejected is the endpoint's verdict, so the flag is written rather than the account retried. Session transcripts go to `~/.claude-profiles/.claudeb/session-logs/<name>.log` in the warm-log format; rotation evidence is journaled to `token-attempts.jsonl` under kinds `session` and `revive`. An unknown account is refused without driving anything, and so is an `auth_needed` account whose token is still missing or expired; an out-of-pool account is not refused at all — that toggle is spend consent (shared-invariants q) — and `claudeb token-fresh <name>` is the read-only question about the same token this path branches on (exit 0 live, 1 expired, 2 unknown account); once the human has logged in, the live token lets revive through to the probe, whose merge clears the flag.

- `bash tests/test_geminib.sh` — `bin/geminib` against fixture profile homes, a fake agy binary, and a fake zero-spend quota helper.

## Reading `~/.llm-limits.json` as an LLM

Treat `stale`, `expired`, `as_of`, and `effective_pct` as the data-honesty contract. Never infer current availability from raw `used_pct` alone: keep it as provenance, check the bucket's `resets_at` against the current time, and refresh before acting on an old or rolled-over frame.

## Display contract (hammerspoon/llm-limits.lua)

- **Gray** = stale bucket (`.stale == true`), or the collector's own `.expired == true`, or the renderer's own render-time check that `resets_at` has already passed (>60s clock-skew tolerance) — this last case covers a window whose reset landed between collects, before the stored `expired` flag catches up. Missing or false `.stale`/`.expired` alone is not gray; a future `resets_at` is never gray.
- **Reset time** = the collector converts raw zero, empty, absent, and 1970-era reset placeholders to `resets_at: null`; Lua renders null/absent as `–`. Any real reset timestamp, including one the renderer now treats as past-due, remains visible as its actual clock time.
- **Refresh failure** = vendor `refresh_error` is `{cause:string,at:epoch}` from the collector, with `needs_user_entry:true` only when every joined cause requires a human account entry. It renders as the same dim `refresh failed <cause> · <age>` line inside that vendor section and persists across passive menu-open collects until that vendor refresh succeeds. Entry-only errors do not raise the global menubar `⚠`; real faults and mixed errors do. The affected account carries the same flag and renders `!` beside its data age. Top-level `refresh_error` keeps the base shape and renders as a red top row; it is reserved for no available vendor data or a full refresh with zero successful vendors. The menu also renders an observed nonzero collector exit as a red runtime error when no cache-level global error exists; any later successful task, including a passive collect, clears that runtime residue after reading a valid cache without a top-level error.
- **Red** = usage warning colors only. Claude rotation metadata is computed locally from the enabled flag and snapshot auth status; wall metadata no longer exists.
- **Fable early warning** = when an `fb` bucket is at least 80%, only its usage-bar substring is red. The rest of the row retains its normal or stale color.
- **Table model and markers** = every row has first-class `5H%`/`WK%`/`FB%` and matching reset columns, plus `AGE`, `ROT`, `CR`, and `STATUS`; there is no `NOTE`. Rows without Fable render `-`. A `~` suffix marks a stale bucket and `!` marks an expired bucket; both may appear, and displayed percentages remain raw `used_pct` values. `AGE` comes from that row's account/vendor `as_of`, which is the oldest timestamp among windows with a numeric `used_pct`; absent and null-valued windows do not participate (`2m`, `1h48m`, and similar).
- **Table rotation and credits** = `ROT` is `off` when the account is out of its vendor's worker pool (all three vendors) — a spend verdict only, never a refresh one: the heartbeat reads an out-of-pool account's usage like any other, `limit-5h`/`limit-weekly`/`fb:limit-fable` when a local effective percentage reaches 100, otherwise `-`. Claude `rotation.usable.general` and `.fable` remain available to worker-pick; the account projection also exposes their general hard gate as `blocked`. `CR` renders a numeric Codex `reset_credits` as `↻N`, including `↻0`.
- **Table status** = `STATUS` is `login needed` for a Codex account with `auth_needed == true`, a Claude account with a present non-`ok` `auth.status`, or a logged-out Gemini profile (`auth_needed == true`, collector-owned status `login needed`); other unavailable rows show their collector-owned status text; all other rows render `-`. A logged-out Gemini profile records its own `refresh_error` cause from the agy helper; a successful profile refresh clears it without changing sibling snapshots.
- **Gemini account rows** = every non-removed profile gets its own account, 5h, and weekly rows; the compact single row survives only for a store without an accounts array. A logged-out profile uses the shared `Log in…`/`Hard refresh`/`Remove <name>` submenu; login opens `geminib profile <name>`, hard refresh targets `gemini/<name>`, and `main` is removed like any other name.
- **Plain model** = each line mirrors the table's labeled 5h/weekly/Fable values and resets, age, rotation, credits, and status. The same `~`/`!` markers apply, expired values are never rewritten to zero, and an unavailable vendor's `last_wall` is appended when present.
- **●** marks the current account from the account block's collector-owned `is_current` flag.
- **In-flight indicator** = passive menu-open collects never render an indicator. Verified-live explicit, hard, and start-window tasks share one registry and prefix the normal menubar title with `⟳ ` immediately; standing vendor or global errors prefix it with `⚠ ` when no explicit task is active. Resume-timer text remains visible. Ordinary entries use a 360s cleanup budget and start-window entries 1200s, but an over-budget task that still reports running remains registered and suppresses duplicates; only a verifiably-dead entry is removed.
- **Checkbox ("In worker pool")** appears on every logged-in real account row of all three vendors (`enabled` = not explicitly excluded) — toggling it calls that vendor's own `enable`/`disable`. It consents to SPEND and nothing else: an excluded account is still refreshed by the heartbeat and `claudeb revive` still takes it. The compact sole-account Gemini row carries it too — no membership is immutable. A **login-needed** row deliberately has none: pool membership on it would claim an availability the account does not have; the stored exclusion survives and reappears once it is logged back in. An explicit/pinned Claude profile entry is not part of `claudeb-store` and so still has no checkbox.
- **"Pin for workers"** on each logged-in account row sets/clears that vendor's `<vendor>_profile=` pin via `<vendor>b use` (`use --clear` when already pinned); a login-needed row offers it only when that account is currently pinned, so a stale pin can always be removed. The row marker `●` means the pin and nothing else — solid when honourable, gray when the pin exists but is lapsed (logged out, removed, blocked, or at limit). A pin absent from the rendered account rows gets a gray clear-only row, so removed profiles and stale configuration remain visible. Pool exclusion alone does not hide a pin.

## Claude Code statusline hooks

`statusline-workdir-hook.sh` (PostToolUse matcher
`Bash|Edit|Write|NotebookEdit|Read|EnterWorktree|ExitWorktree`, plus a PreToolUse matcher
`Bash|Task|Agent` — `Bash` there only to snapshot the worktree list a `git worktree add` is
diffed against, so a PreToolUse registration without it kills that path whole) records the git toplevel a session actually works in; the status line shows it with a
magenta `»` marker when it differs from the launch repo. That is the only question it answers:
which changed paths are THIS chat's work is the commit journal's (`<common-dir>/claude-commit-journal`
— one ledger per checkout family, wherever in it the write happened —
`<session>TAB<epoch>TAB<path>`), and the `touched-<session_id>` file this hook used to write beside
it had no reader left once the review segment became the review gate's mouthpiece.
Rules:
- Events carrying `agent_id`/`agent_type` report the PARENT `session_id`, so a subagent's Bash,
  Read, dispatch (and every non-write tool) is ignored — a worker's stray `cd` must never retarget
  the parent's display, and an Explore agent reads across every repo it can reach. Its
  Edit/Write/NotebookEdit events do count, but only through the sustained-work run
  below: three writes in a row into the same other toplevel, in ANY home (worktree or not),
  since a worker starts where it was dispatched, not where the session lives. With no state file
  at all a subagent write adopts its toplevel at once, like any other event.
- Task/Agent (the dispatch tool, named either way depending on harness version) is heard on
  PreToolUse only — in orchestrator mode the worker's edits happen in a process that reports
  nothing, so the brief is the only signal, and hearing the PostToolUse replay too would count one
  dispatch twice. The first ten `/`-rooted tokens of `tool_input.prompt` + `.description` are
  scanned and the FIRST that clears the exclusions and `cd`s into a git repo wins (briefs name the
  worker's cwd early; a file path does not resolve). It is write-grade evidence from the session:
  immediate on a non-worktree home, through the run against a worktree pin.
- Read (main session only, `file_path` dirname'd) is the weakest evidence and never retargets at
  once: three consecutive reads into the same other toplevel, in ANY home. With no state file it is
  ignored — a home is seeded by SessionStart or adopted by a write, never established by a lookup —
  and a read back home neither rewrites the home nor clears a run in progress, but does interrupt
  it (its toplevel is appended onto an existing run, never onto an empty one), since without that
  the three need not be consecutive and scattered lookups alone would move the home.
- Bash: the LAST `cd`/`git -C` in the command wins (`;`, `&`, `|`, `&&`, `||`, `(`-subshell, and
  newline-separated all match; `(cd /path && cmd)` is the form the cd-guard hook prescribes).
  A winning cd that sits after `(` is a subshell one and dies with the command — the session's
  own cwd never moves — so it retargets only through the same sustained-work run: three
  consecutive subshell cds into the SAME toplevel (a worktree-pinned home ignores them entirely).
  A persistent `cd`/`pushd`, and `git -C <dir>`, still retarget on the first one, and the
  persistent cd is the one thing besides sustained work that breaks a worktree pin: cd-guard
  denies every persistent cd a session has not unlocked, so one that arrives is a deliberate
  move. `git -C <dir>` counts only when followed by a mutating
  subcommand (worktree/checkout/switch/commit/merge/rebase/cherry-pick/revert/restore/stash/
  am/reset/pull); read-only `git -C ... status/log/diff` never retargets.
- A Bash `git worktree add` is the one command also heard on PreToolUse, where it snapshots the
  worktree lists of the `-C` dir, the session cwd and the current home into
  `workdir-<sid>.wtadd`; the PostToolUse diff of that union names the created path (the command
  text cannot — `... worktree add $N` expands in the shell), and exactly one new path retargets,
  a failed or ambiguous add nothing. No snapshot falls back to the parsed token.
- EnterWorktree records the toplevel of the `worktree at <absolute path>` in `.tool_response`
  (string or object); ExitWorktree deletes the session's state file. tmp/system/`~/.claude*`/
  node_modules paths are excluded; records older than 7 days are pruned.
- Also registered for SessionStart: `source` `startup`/`resume`/`clear` clears the session's
  workdir state file and re-seeds it from the starting cwd's git toplevel (without a seed the
  first cd anywhere would adopt THAT dir as home, and worktree stickiness can only protect a
  home that already exists); `resume` is the one exception — ANY home that still resolves as its
  own git toplevel is kept, worktree or main checkout alike, because the resume cwd is where the
  chat was relaunched (usually the main checkout), not where its work lives; a surviving
  directory is not enough (a worktree without its `.git` link, or any subdirectory, resolves up
  into the owning checkout, whose branch would then be shown as the workspace); `compact` keeps it — the shell and its
  cwd survive `/compact`. This runs before the agent filter on purpose: `agent_type` on
  SessionStart means a top-level `claude --agent` session, not a subagent.
The statusline itself unlinks a state file that no longer points at a git dir.

State files are stored at:
- `~/.cache/claude-statusline/workdir-<session_id>`
- `~/.cache/claude-worker-tags/<agent_id>`

`worker-tag-hook.sh` derives the actual relay account/model/effort from Codex, claudeb, or `geminib profile`
launch commands and prefixes the tag onto later Bash activity descriptions for `codex-worker`,
`claudeb-worker`, and `gemini-worker` agents. It exits
silently for any `hook_event_name` other than PreToolUse (its rewrite payload hardcodes
`hookEventName: "PreToolUse"`, so a mis-registration must be a no-op).

`limits-triage-nudge.sh` (PostToolUse matcher `Bash`) scans Bash tool output for a limit-shaped
pattern (`no available accounts`, `API Error: 503/529`, `usage limit`, `overloaded`,
`anthropic-ratelimit`, `CLAUDEB_USAGE_LIMIT`, `claudeb ... timed out`) alongside a
claude/claudeb/anthropic/fable context word in the same output, and nudges the session to run
`llm-limits --table --no-write` instead of theorizing. Dedup: one nudge per session per
15 minutes, state in `/tmp/claude-limits-triage-nudge-<session_id>`.

To disable any of these hooks, remove its entry from `hooks.PostToolUse` or `hooks.PreToolUse` in
`~/.claude/settings.json`.
